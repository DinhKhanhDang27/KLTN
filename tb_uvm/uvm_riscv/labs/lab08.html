Tổng quan lab
  • Lab này làm gì: viết SVA kiểm các bất biến của core: PC tuần tự (+4) trừ khi rẽ nhánh/stall, PC giữ khi stall, PC = đích khi redirect, đích nhảy căn chỉnh, và bất biến ISA x0 ≡ 0. Gắn checker vào DUT bằng bind (không sửa RTL).
  • Tạo ra file nào: tb/sva/riscv_protocol_checker.sv (checker pipeline), tb/sva/riscv_regfile_checker.sv (x0), và các lệnh bind trong tb/sva/riscv_bind.sv.
  • Nhận gì từ lab trước: chương trình hỗn hợp (Lab 7) làm stimulus.
  • Lab sau dùng để làm gì: SVA bắt lỗi "cấu trúc/đồng bộ"; scoreboard (Lab 10) bắt lỗi "giá trị". Hai lớp bổ trợ nhau.
Trọng tâm UVM của lab
  • SVA sống ở module-world: không phải component UVM; chạy song song và độc lập phase/objection.
  • Cầu nối sang UVM: $error không tăng bộ đếm UVM_ERROR → “PASS giả”. Cách đưa lỗi assertion vào uvm_report_server.
  • bind để gắn checker không sửa RTL; điều khiển bật/tắt checker từ UVM (config knob).
  • Vacuity & cover: assertion “pass” vì antecedent không bao giờ xảy ra là vô nghĩa — cần cover property.
  • Phân vai SVA ↔ scoreboard ↔ coverage: SVA = thời gian/cấu trúc, scoreboard = giá trị.
Pipeline-specific: khác single-cycle, PC +4 chỉ đúng khi không redirect/stall; có disable iff(rst) và dùng $past vì hiệu ứng đến ở chu kỳ sau (|=>). jalr chỉ xóa bit0 → đích có thể lệch 4 (chỉ căn 2) — một điểm tinh tế ta assert bit0==0 và ghi chú.

6. Lý thuyết ngắn — property & bind (+ tích hợp UVM)

  1. Concurrent assertion chạy mỗi sườn clock, độc lập UVM. Fail → UVM_ERROR/ $error + thời điểm.
  2. |-> vs |=>: a |-> b kiểm b ngay chu kỳ a đúng; a |=> b kiểm b ở chu kỳ kế tiếp — dùng cho hiệu ứng pipeline (PC cập nhật ở sườn sau).
  3. $past: nhìn lại 1 chu kỳ — so sánh PC hiện tại với PC trước +4.
  4. bind: đặt checker "bên trong" DUT nhưng viết ở TB. Port map tham chiếu net nội bộ của module đích (vì instance nằm trong scope đó).

6.5. SVA và UVM report server — cái bẫy “PASS giả”

$error in ra log nhưng không đi qua uvm_report_server. Dòng tổng kết UVM_ERROR : 0 chỉ đếm báo cáo UVM. Hệ quả: một assertion fail liên tục mà regression script vẫn grep thấy “UVM_ERROR : 0” và đánh PASS.

Cách 1 — gọi report API từ module (không cần class):

import uvm_pkg::*;                       // trong module checker
`include "uvm_macros.svh"
a_pc_inc: assert property (p_pc_inc)
  else `uvm_error("SVA_PC", $sformatf("PC khong +4 @%0t", $time))

Macro `uvm_error dùng uvm_report_enabled + uvm_report_error với context toàn cục (uvm_root::get()), nên hợp lệ ngoài class. Cách 2 — giữ checker độc lập UVM, đếm lỗi bằng một biến (sva_fail_cnt++ trong nhánh else), rồi cuối test đối chiếu và gọi uvm_report_error từ check_phase.

Bẫy kép: regression script phải kiểm cả UVM_ERROR : 0 và UVM_FATAL : 0 và không có dòng Error:/$error của assertion — hoặc chuyển assertion vào UVM report như trên để một chỗ kiểm duy nhất.

6.6. Điều khiển checker từ UVM

Có lúc phải tắt assertion hợp lệ (negative test cố ý vi phạm bất biến, reset giữa chừng):

  • $assertoff(0, tb.dut) / $asserton / $assertkill gọi từ initial hoặc từ test (task trong interface bọc lại).
  • Knob qua config: checker đọc uvm_config_db#(bit)::get(null,"","en_sva",en) trong initial (null context được phép khi đọc), mặc định bật.
  • Dùng disable iff (rst || !en_sva) trong property.

6.7. Vacuity, cover và kiểm chứng chính checker

  • Vacuous pass: a |-> b “đúng” khi a sai. Nếu a không bao giờ xảy ra (chương trình không có branch), assertion pass mãi mãi mà chưa kiểm gì.
  • Luôn kèm cover property (antecedent) hoặc cover property (a ##1 b) để chứng minh property đã được “thử” — kết quả hiện trong coverage report (Lab 12/15).
  • “Assertion phải fail được”: Iteration 1 cố ý sai để thấy fail — mutation testing mức nhỏ cho checker.

7. Iteration 0 — checker pipeline + regfile

tb/sva/riscv_protocol_checker.sv 
// tb/sva/riscv_protocol_checker.sv — kiểm giao thức PC/redirect/stall tầng IF
`ifndef RISCV_PROTOCOL_CHECKER_SV
`define RISCV_PROTOCOL_CHECKER_SV
module riscv_protocol_checker (
  input        clk,
  input        rst,
  input [31:0] pc_if,
  input        redirect,
  input        stall,
  input [31:0] redirect_target,
  input        memwb_reg_write,
  input [4:0]  memwb_rd
);

  // 1) PC +4 khi không redirect và không stall
  //    `!rst` trong antecedent là BẮT BUỘC: driver nhả rst bằng NBA ngay tại posedge, nên ở tick cuối cùng của reset
  //    `disable iff(rst)` (giá trị hiện tại = 0) không còn chặn, nhưng antecedent (giá trị đã sample = reset) vẫn "đúng"
  //    -> consequent so PC lúc reset với PC +4 -> false fail đúng 1 lần @ thời điểm nhả reset (đã gặp khi chạy thật).
  property p_pc_inc;
    @(posedge clk) disable iff(rst) (!rst && !redirect && !stall) |=> (pc_if == $past(pc_if) + 32'd4);
  endproperty
  a_pc_inc: assert property(p_pc_inc)
    else $error("[SVA] PC khong +4 khi khong redirect/stall @%0t", $time);

  // 2) PC giữ khi stall (và không redirect)
  property p_pc_stall;
    @(posedge clk) disable iff(rst) (stall && !redirect) |=> $stable(pc_if);
  endproperty
  a_pc_stall: assert property(p_pc_stall)
    else $error("[SVA] PC khong giu khi stall @%0t", $time);

  // 3) Khi redirect: PC chu kỳ sau = redirect_target của chu kỳ này
  property p_redirect_tgt;
    @(posedge clk) disable iff(rst) redirect |=> (pc_if == $past(redirect_target));
  endproperty
  a_redirect_tgt: assert property(p_redirect_tgt)
    else $error("[SVA] PC != redirect_target sau redirect @%0t", $time);

  // 4) Đích nhảy căn chỉnh tối thiểu 2 byte (RV32I: branch/jal căn 4; jalr xóa bit0)
  property p_tgt_align;
    @(posedge clk) disable iff(rst) redirect |-> (redirect_target[0] == 1'b0);
  endproperty
  a_tgt_align: assert property(p_tgt_align)
    else $error("[SVA] redirect_target le (bit0=1) @%0t", $time);

  // 5) Ghi WB vào x0 là vô nghĩa — nếu reg_write ở WB thì rd nên != 0
  //    (JAL/JALR rd=x0 vẫn hợp lệ nhưng regfile bỏ qua -> cảnh báo mức thấp)
  property p_wb_x0_note;
    @(posedge clk) disable iff(rst) (memwb_reg_write && (memwb_rd == 0)) |-> 1'b1; // luôn pass, chỉ cover
  endproperty
  c_wb_x0: cover property(p_wb_x0_note);

endmodule
`endif
$error không phải UVM_ERROR. Checker ở Lab này dùng $error nên độc lập UVM; hệ quả: dòng tổng kết UVM_ERROR : 0 vẫn có thể PASS giả dù assertion đã fail. Xem §6 (UVM integration) để chuyển lỗi vào report server.
tb/sva/riscv_regfile_checker.sv (x0 ≡ 0) 
`ifndef RISCV_REGFILE_CHECKER_SV
`define RISCV_REGFILE_CHECKER_SV
module riscv_regfile_checker (
  input        clk,
  input        rst,
  input        reg_write,
  input [4:0]  write_reg,
  input [31:0] regx0        // = registers[0]
);
  // x0 luôn 0 sau reset
  a_x0_zero: assert property(@(posedge clk) disable iff(rst) (regx0 == 32'd0))
    else $error("[SVA] x0 != 0 @%0t (= 0x%08h)", $time, regx0);

  // không bao giờ xảy ra ghi thực sự vào x0 (guard reg_write && write_reg!=0)
  // -> cover trường hợp reg_write=1 & write_reg=0 để biết nó CÓ xảy ra mà vẫn an toàn
  c_wr_x0: cover property(@(negedge clk) disable iff(rst) (reg_write && write_reg==0));
endmodule
`endif

Iteration 1 — cố ý sai property để thấy fail (sanity của checker)

Iteration 2 — thêm property: sau redirect, IF/ID bị flush (ifid_valid=0 chu kỳ sau)

Khác biệt

Kiểm đúng cơ chế flush của pipeline. Dạy: SVA soi được micro-architecture, không chỉ ISA.

Iteration 3 — thêm property forwarding: khi fwdA_exmem, operand = exmem_ex_nonmem

Bind thêm các net forwarding; assert fwdA_exmem |-> (alu_a_ex == exmem_ex_nonmem).

Khác biệt

Kiểm đường forwarding — lỗi hazard kinh điển. Dạy: property cho datapath nội bộ.

Khác biệt

Tránh false-fail khi stall giữ trạng thái. Dạy: chọn điều kiện disable đúng ngữ cảnh.

Khác biệt

12. Phỏng vấn — hỏi & đáp

Bấm câu hỏi để xem đáp án — nên tự trả lời miệng trước khi mở. Mỗi câu có ví dụ cụ thể như khi bị hỏi trong phỏng vấn.

Assertion fail nhưng báo cáo cuối vẫn “UVM_ERROR : 0”. Vì sao và xử lý ra sao?

Vì $error của SVA không đi qua uvm_report_server — bộ đếm UVM chỉ tăng với `uvm_error/uvm_report_error. Cách xử lý: (1) dùng `uvm_error trong nhánh else của assertion (cần import uvm_pkg::* + include macros); hoặc (2) giữ $error, đếm lỗi bằng biến rồi cuối test đối chiếu để gọi uvm_report_error; (3) script regression grep cả log của simulator.

a_x0: assert property (@(posedge clk) disable iff (rst) regx0 == 0)
  else `uvm_error("SVA_X0", $sformatf("x0=%08h @%0t", regx0, $time))
Giải thích |-> và |=> kèm ví dụ về PC. Vì sao dùng $past?

a |-> b: nếu a đúng ở chu kỳ t thì b phải đúng cùng t. a |=> b ≡ a |-> ##1 b: b ở chu kỳ kế tiếp. PC cập nhật ở sườn sau, nên “không stall/redirect ở t ⇒ PC(t+1) = PC(t)+4” viết bằng |=> và $past(pc_if) (giá trị chu kỳ trước) để so với PC mới.

(!redirect && !stall) |=> (pc_if == $past(pc_if) + 32'd4)
bind là gì, vì sao dùng thay vì viết assertion trong RTL?

bind chèn một instance checker vào trong phạm vi của module đích từ bên ngoài, nên port map thấy được net nội bộ (pc_if, memwb_reg_write_r) mà không sửa RTL. Lợi: RTL sạch (không lẫn code verify, không ảnh hưởng tổng hợp), bật/tắt bằng cách đưa/bỏ file bind, tái dùng cho nhiều DUT (bind theo tên module). Nhược: tên net nội bộ đổi → lỗi bind; gỡ lỗi phải biết phạm vi.

Làm sao tắt một assertion trong một test cụ thể (negative test)?

Ba mức: (1) $assertoff(0, path) từ test/interface task — nhanh; (2) knob trong disable iff (!en) đọc từ config — rõ ràng, có thể bật lại; (3) tách file bind theo nhóm (protocol vs isa) và chỉ biên dịch nhóm cần. Quan trọng: tắt có chủ đích, có log (“SVA a_tgt_align OFF for negative_test”) để review regression không nhầm.

Vacuous pass là gì? Cho ví dụ trong lab này và cách phát hiện.

Assertion “pass” vì antecedent không bao giờ đúng. Ví dụ redirect |=> pc_if == $past(redirect_target) chạy trên chương trình toàn R-type: redirect không xảy ra → pass vô nghĩa. Phát hiện: thêm cover property (redirect), hoặc báo cáo assertion “vacuous count”; trong coverage report phải thấy antecedent đã được hit ≥1 lần.

disable iff(rst) dùng để làm gì? Sai thế nào khi đặt nhầm điều kiện?

Tắt đánh giá (và hủy attempt đang chạy) khi reset để tránh false-fail trong lúc trạng thái chưa xác định. Đặt nhầm: nếu dùng disable iff (stall) cho property “PC giữ khi stall” thì chính trường hợp cần kiểm bị tắt → assertion vô hiệu. Quy tắc: chỉ disable theo reset/điều kiện ngoài phạm vi property.

SVA trong interface so với trong module bind — chọn thế nào?

Trong interface: kiểm tra giao thức tại ranh giới (X-check, valid/ready) — đi theo interface khi tái dùng VIP, có thể bật/tắt qua config của interface. Bind: kiểm tra nội bộ DUT (forwarding, flush, x0) — không sửa RTL, theo DUT cụ thể. Trong UVM hoàn chỉnh: assertion ranh giới đi cùng agent (has_checker trong cfg), assertion nội bộ là một lớp riêng của dự án.

Assertion có thay được scoreboard không?

Không. SVA mạnh với thuộc tính theo thời gian nhưng không so được dữ liệu với một mô hình tham chiếu phức tạp (ISS). Scoreboard bắt lỗi giá trị; SVA bắt lỗi giao thức/cấu trúc ngay tại chu kỳ gây lỗi (định vị chính xác hơn). Hai lớp bổ trợ; coverage quyết định đã thử đủ chưa.

14. Bài tập code & câu hỏi nâng cao UVM

8 bài rèn tay, tăng dần độ khó. Làm trên baseline của lab này; đáp án chỉ là hướng tham khảo — giá trị nằm ở việc bạn tự gõ, chạy và đọc log.

0 / 8 bài đã làm
★ Dễ

EX1 — Chuyển sang UVM_ERROR

Sửa riscv_protocol_checker dùng `uvm_error (import uvm_pkg::*). Chạy bản cố ý sai +8 và xác nhận UVM_ERROR tăng. So với bản $error.
Gợi ý & đáp án tham khảo

Bản $error: log có lỗi nhưng summary UVM_ERROR : 0. Bản uvm_error: summary > 0 và có thể dùng set_max_quit_count().

★ Dễ

EX2 — Thêm cover cho antecedent

Thêm cover property (@(posedge clk) disable iff (rst) redirect); và tương tự cho stall. Chạy rtype_test rồi branch_test. So sánh số hit.
Gợi ý & đáp án tham khảo

rtype_test: hit = 0 → các assertion về redirect đang vacuous. Bài học: assertion pass ≠ đã kiểm.

★★ Vừa

EX3 — Knob bật/tắt từ test

Trong checker, thêm bit en = 1; initial void'(uvm_config_db#(bit)::get(null,"","en_sva",en)); và dùng disable iff (rst || !en). Test âm set(null,"*","en_sva",0). Có chạy đúng không? (Gợi ý: thứ tự initial trong module so với run_test).
Gợi ý & đáp án tham khảo

Rủi ro race: initial của checker có thể chạy trước khi test set. Giải pháp: đọc trong always @(posedge clk) hoặc dùng #0/event; hoặc tắt bằng $assertoff từ test trong run_phase.

★★ Vừa

EX4 — Property cho flush

Thêm port ifid_valid, idex_valid và property: redirect |=> (!ifid_valid) và redirect |=> ##1 (!idex_valid). Cố ý hỏng flush trong RTL (copy) rồi để SVA bắt.
Gợi ý & đáp án tham khảo

Kiểm tra bằng mutation: SVA phải fail khi RTL sai. Nếu không fail → property quá yếu hoặc không đủ stimulus (cần cover).

★★ Vừa

EX5 — Forwarding assertion

Bind các net forwarding và assert: fwdA_exmem |-> (alu_a_ex == exmem_ex_nonmem). Viết một chương trình có chuỗi phụ thuộc (add x1; add x2,x1; add x3,x2) để chắc property được “thử”. Thêm cover.
Gợi ý & đáp án tham khảo

Dùng riscv_prog_base_seq với gen_one chọn rs1 = rd của lệnh trước (biến trạng thái trong sequence) để ép phụ thuộc — tình huống stimulus thông minh đầu tiên của bạn.

★★ Vừa

EX6 — Tắt assertion có log

Viết một task trong interface disable_sva(string why) gọi $assertoff và in `uvm_warning("SVA_OFF", why). Dùng trong negative_opcode_test.
Gợi ý & đáp án tham khảo

Tắt có chủ đích, có log: reviewer thấy được test nào đã nới kiểm tra. Nhớ có enable_sva() để bật lại ở cuối.

★★★ Khó

EX7 — Assertion-only environment

Chạy DUT không có scoreboard (+UVM_TESTNAME=mixed_test với env đã tắt SB) để xem SVA độc lập có đủ phát hiện lỗi ALU không. Rút ra kết luận về phân vai SVA/scoreboard.
Gợi ý & đáp án tham khảo

SVA ở lab chỉ kiểm PC/flush/x0 → không thấy lỗi giá trị ALU. Kết luận: cần scoreboard; hoặc phải viết property giá trị (ví dụ add) — thường là overkill so với ISS.

★★★ Khó

EX8 — Mutation matrix

Lập bảng 5 lỗi cố ý chèn vào RTL (sai +4, quên stall, sai target, ghi x0, sai forwarding) × 3 cơ chế bắt (SVA, scoreboard, coverage). Chạy và điền: cơ chế nào bắt được lỗi nào.
Gợi ý & đáp án tham khảo

Kết quả điển hình: PC/flush → SVA; giá trị → scoreboard; “chưa từng thử” → coverage. Bảng này là câu trả lời mạnh cho “vì sao cần cả ba”.
