Tổng quan lab (capstone)
  • Lab này làm gì: ráp mọi thứ thành một môi trường "portfolio": (1) Makefile/run.tcl biên dịch + chạy; (2) regression nhiều test × nhiều seed; (3) lưu + hợp nhất coverage (xsim -cov + xcrg); (4) chạy firmware thật (load_hex) end-to-end self-check; (5) verification plan ánh xạ tính năng ↔ test ↔ coverage; (6) nâng cao: đổi DUT sang riscv_avalon_wrapper với agent Avalon-MM bên bộ nhớ + uvm_reg thật.
  • Tạo ra file nào: scripts/Makefile, scripts/run.tcl, scripts/regress.sh, firmware firmware/*.hex, tài liệu plan.
  • Nhận gì từ lab trước: toàn bộ Lab 1–14.
  • Sản phẩm: testbench UVM hoàn chỉnh verify RV32I pipeline, chạy regression + coverage.
Trọng tâm UVM của lab
  • Vòng đời một lần chạy UVM từ command line: +UVM_TESTNAME, +UVM_VERBOSITY, +UVM_TIMEOUT, +UVM_MAX_QUIT_COUNT, plusarg tự định nghĩa qua uvm_cmdline_processor.
  • Tiêu chí pass/fail bền vững: severity count + “đã làm việc thật”; không dựa vào một dòng log mong manh.
  • Random stability & tái lập: seed, vì sao thêm một component có thể đổi stimulus.
  • Coverage closure (merge, đọc báo cáo, nhắm bin trống) và vPlan như hợp đồng verify.
  • Tái dùng: agent PASSIVE/ACTIVE, đóng gói UVC, mang khung sang UART/I2C (mục 15).
  • Đã sửa regress.sh: log summary của UVM là UVM_ERROR : 0 (nhiều dấu cách), kiểm cả UVM_FATAL, có timeout, lưu seed lỗi.

6. Lý thuyết ngắn — đóng vòng verify (+ UVM trong regression)

  1. Đóng vòng: stimulus (seq/vseq) → DUT → monitor retire → scoreboard (ISS) + assertion + coverage. Regression chạy nhiều seed để coverage hội tụ & lộ lỗi hiếm.
  2. Coverage merge: mỗi lần chạy sinh 1 DB; xcrg gộp lại → bức tranh tổng. Mục tiêu: 100% functional (ISA+hazard) + code coverage cao, 0 lỗi.
  3. Firmware thật: chương trình đã dịch (counter, tổng mảng…) nạp qua load_hex; self-check so DUT↔ISS trên chính firmware đó.
  4. vPlan: tài liệu sống nối yêu cầu ↔ bằng chứng (test + coverage) — đóng dự án khi mọi dòng "Done".

6.6. Pass/fail — cách kết luận đáng tin

  1. UVM_ERROR = 0 và UVM_FATAL = 0 (đọc từ uvm_report_server hoặc grep log).
  2. Đã làm việc thật: số lệnh so > 0, coverage tối thiểu, sự kiện “halt” đã thấy.
  3. Assertion SVA đã chuyển vào UVM report (Lab 8) hoặc grep thêm log simulator.
  4. Exit code của tiến trình + timeout bao ngoài (timeout 600) để một test treo không làm treo cả regression.
“Xanh giả” hay gặp: (a) chỉ grep UVM_ERROR : 0 bỏ sót UVM_FATAL; (b) regex không khớp định dạng thật nên luôn ra FAIL hoặc luôn ra PASS; (c) test kết thúc ở time 0 (quên objection) nhưng 0 lỗi; (d) assertion dùng $error.

6.7. Random stability — tái lập lỗi

UVM gieo seed cho từng object dựa trên đường dẫn hierarchy + tên + thứ tự tạo (random stability). Cùng seed + cùng cấu trúc ⇒ cùng stimulus. Nhưng thêm/bớt một component hoặc một lời gọi randomize() trong thread khác có thể đổi dòng random của các thành phần khác. Quy tắc thực hành: (1) log seed và tên test ở đầu mỗi run; (2) lưu failed_seeds.txt; (3) khi sửa TB, chạy lại để thấy bug có còn tái hiện hay không (có thể “biến mất” vì đổi random — không có nghĩa là đã sửa).

6.8. Coverage closure — vòng lặp

chạy N seed ──► merge (xcrg) ──► đọc bin thiếu ──► (1) test directed nhắm bin
      ▲                                         (2) nới/đổi constraint (dist)
      └─────────────────── lặp ◄────────────────  (3) bin không thể chạm → ignore/loại + ghi lý do vào vPlan

Kết thúc khi: functional = mục tiêu, bin còn trống đều có lý do được duyệt, 0 lỗi, và vPlan mọi dòng “Done” (hoặc “Known limitation” có chữ ký).

6.9. Tái dùng khung UVM

  • UVC đóng gói: agent + config + sequences + interface + coverage trong package riêng; không phụ thuộc env cụ thể.
  • Vertical reuse: block-level ACTIVE → system-level PASSIVE (Lab 5).
  • Horizontal reuse: cùng khung cho UART/I2C/SPI (mục 15): chỉ thay interface, item, driver/monitor, ref model.

scripts/regress.sh (nhiều test × seed + merge coverage) 
#!/usr/bin/env bash
# scripts/regress.sh  — chạy từ sim/
set -u
TESTS="rtype_test itype_test ls_test branch_test jump_test upper_test \
       mixed_test self_check_test negative_opcode_test ral_test"
SEEDS="${SEEDS:-1 2 3 4 5}"
make -f ../scripts/Makefile comp || exit 1
pass=0; fail=0; : > failed_seeds.txt
for t in $TESTS; do
  for s in $SEEDS; do
    log=run_${t}_${s}.log
    echo "== $t seed=$s =="
    # ghi log ra file rồi grep (không dùng grep -q trong pipe với tee: SIGPIPE có thể cắt log)
    timeout 600 xsim top_sim -R -cov_db_name ${t}_${s} -sv_seed $s \
      -testplusarg "UVM_TESTNAME=$t" -testplusarg "UVM_TIMEOUT=2000000,NO" > "$log" 2>&1
    rc=$?
    # Summary của UVM in dạng  "UVM_ERROR :    0"  (nhiều dấu cách) → dùng regex, kiểm cả FATAL,
    # và yêu cầu scoreboard đã so ít nhất 1 lệnh (chống "xanh giả" khi test chạy rỗng).
    if [ $rc -eq 0 ] && grep -Eq "UVM_ERROR *: *0$" "$log" && grep -Eq "UVM_FATAL *: *0$" "$log" \
       && grep -Eq "\[SB\] PASS" "$log"; then
      pass=$((pass+1))
    else
      fail=$((fail+1)); echo "$t $s" >> failed_seeds.txt; echo "FAIL: $t seed=$s (log: $log)"
    fi
  done
done
echo "PASS=$pass FAIL=$fail   (xem failed_seeds.txt để tái lập: lặp lại đúng test + seed)"
# hợp nhất coverage
xcrg -dir xsim.covdb -report_format html -report_dir cov_report || true     # gộp mọi DB <test>_<seed>
echo "Coverage report: cov_report/dashboard.html"

tb/test/firmware_test.sv 
`ifndef FIRMWARE_TEST_SV
`define FIRMWARE_TEST_SV
// Chạy firmware thật: agent PASSIVE (không driver/sequencer), test tự giữ reset, nạp hex bằng backdoor, nhả reset.
// Monitor + scoreboard (ISS exec theo instr retire) + coverage vẫn chạy như bình thường.
class firmware_test extends riscv_base_test;
  `uvm_component_utils(firmware_test)
  string fw = "firmware/counter.hex";
  function new(string n, uvm_component p); super.new(n,p); endfunction

  function void build_phase(uvm_phase phase);
    super.build_phase(phase);                 // base_test tạo cfg + env (agent chưa build)
    cfg.is_active = UVM_PASSIVE;              // agent đọc cfg ở build_phase của chính nó (sau test) nên đổi được ở đây
    void'($value$plusargs("FW=%s", fw));
  endfunction

  task run_phase(uvm_phase phase);
    phase.raise_objection(this);
    cfg.vif.rst <= 1'b1;
    cfg.vif.clear_imem();
    cfg.vif.load_hex(fw);                     // $readmemh vào ROM
    repeat (3) @(posedge cfg.vif.clk);
    cfg.vif.rst <= 1'b0;
    repeat (150) @(posedge cfg.vif.clk);      // 10 vòng lặp x ~3-4 chu kỳ + pipeline + sw
    `uvm_info("FW", $sformatf("x1=%0d mem[0]=%0d (mong 10, 10)", cfg.vif.peek_reg(1), cfg.vif.peek_mem(0)), UVM_LOW)
    if (cfg.vif.peek_reg(1) !== 32'd10 || cfg.vif.peek_mem(0) !== 32'd10)
      `uvm_error("FW", "firmware counter sai ket qua")
    env.sb.final_check();
    phase.drop_objection(this);
  endtask
endclass
`endif

firmware_test.sv đã nằm trong riscv_pkg.sv ở trên. Chạy: xsim top_sim -R -testplusarg UVM_TESTNAME=firmware_test. Kết quả đã chạy: [FW] x1=10 mem[0]=10 (mong 10, 10), [SB] SWEEP PASS ... (retire=58), UVM_ERROR : 0.

10. Nâng cao — đổi DUT sang riscv_avalon_wrapper + uvm_reg

riscv_avalon_wrapper bọc riscv_pipeline_core và phơi data memory qua Avalon-MM (avm_address/read/readdata/readdatavalid/write/writedata/byteenable/ waitrequest). Đây là bước nâng DUT từ "busless" lên "có bus":

  1. Cần memory model + Avalon agent: core giờ đọc/ghi qua bus → TB phải cấp một Avalon slave (RAM model) đáp readdatavalid/waitrequest. Thêm avalon_if + avalon_agent (driver đáp bus, monitor sample giao dịch).
  2. uvm_reg thật: map các word RAM thành uvm_reg trong uvm_reg_block; viết uvm_reg_adapter (reg↔Avalon) + uvm_reg_predictor. Khi đó frontdoor = truy cập bus qua adapter, backdoor = hierarchical — RAL chuẩn thay cho "RAL-like" Lab 13.
  3. Top đổi: riscv_avalon_wrapper dut(.clk,.reset_n(~rst),...) nối avalon_if; instruction fetch vẫn nội bộ (u_core.u_imem) nên backdoor nạp ROM giữ nguyên (...dut.u_core.u_imem.mem). Shadow retire bám tín hiệu của u_core (có thêm exmem_valid, mem_stall).
  4. Vì sao để sau cùng: thêm 1 lớp giao thức bus (handshake 2 pha) — lớn hơn hẳn; nên làm khi đã vững khung UVM. Đây cũng là nơi bộ lab AXI4 gốc (handshake VALID/READY) nối lại với RISC-V.
Lưu ý path backdoor đổi tiền tố khi dùng wrapper: dut.u_core.u_imem.mem / dut.u_core.u_regfile.registers / dut.u_core.u_dmem... (nhưng với Avalon, data memory là RAM model của TB trên bus, không còn u_dmem trong core — core chỉ phát bus). Điều chỉnh riscv_if peek cho phù hợp.

12. Phỏng vấn — hỏi & đáp

Bấm câu hỏi để xem đáp án — nên tự trả lời miệng trước khi mở. Mỗi câu có ví dụ cụ thể như khi bị hỏi trong phỏng vấn.

Một regression gồm những thành phần nào? Bạn đảm bảo nó “đáng tin” thế nào?

Test list × seed list, script chạy song song (hoặc tuần tự) có timeout, lưu log/seed lỗi, gom pass/fail, merge coverage, báo cáo tóm tắt. Đáng tin khi: (1) tiêu chí pass/fail chặt (ERROR=0, FATAL=0, đã so > 0); (2) mọi test có watchdog; (3) kiểm chứng regression bằng một lỗi RTL cố ý — phải ra FAIL; (4) tái lập được: seed + lệnh được ghi lại.

Vì sao regress.sh cũ grep UVM_ERROR : 0 có thể sai? Sửa thế nào?

Report server in dạng UVM_ERROR : 0 (căn lề nhiều dấu cách), nên pattern một dấu cách không khớp ⇒ mọi test bị coi FAIL (hoặc, đảo lại, nếu grep ngược thì luôn PASS). Ngoài ra bỏ qua UVM_FATAL. Sửa: grep -Eq "UVM_ERROR *: *0$" và "UVM_FATAL *: *0$", ghi log ra file rồi grep (không grep -q trong pipe với tee — SIGPIPE có thể cắt log).

Giải thích random stability của UVM. Một bug biến mất khi bạn thêm một dòng log — nghĩa là gì?

Seed của object được suy ra từ đường dẫn hierarchy và thứ tự tạo, nên cùng seed + cùng cấu trúc ⇒ cùng stimulus. Thêm dòng log thuần không ảnh hưởng random; nhưng thêm randomize(), component hoặc $urandom vào thread khác có thể dịch chuyển chuỗi random ⇒ stimulus khác ⇒ bug “biến mất” vì không còn được kích thích, chưa phải đã sửa. Cách xử lý: tái hiện bằng test directed hoặc bằng cách khóa stimulus (ghi lại chương trình dạng hex).

+UVM_TIMEOUT khác set_drain_time khác phase_ready_to_end thế nào?

+UVM_TIMEOUT: watchdog tuyệt đối — hết giờ là UVM_FATAL (test treo). set_drain_time: thời gian chờ cố định sau khi objection về 0 để DUT/monitor xả nốt. phase_ready_to_end: callback cho phép component trì hoãn kết thúc có điều kiện (còn pending). Ba lớp khác mục đích: an toàn, chờ cố định, chờ thông minh.

Bạn đưa coverage closure vào quy trình thế nào? Bin không thể chạm được xử lý ra sao?

Chạy nhiều seed → merge → phân loại bin trống: (1) thiếu stimulus ⇒ viết directed/chỉnh dist; (2) không thể xảy ra (tổ hợp cấm theo ISA) ⇒ ignore_bins + ghi lý do + review; (3) coverage model sai ⇒ sửa model. Không bao giờ xóa bin chỉ để đạt 100%. Mọi ngoại lệ ghi vào vPlan.

Vì sao firmware thật chạy qua agent PASSIVE thay vì ACTIVE?

Stimulus là firmware đã dịch nạp bằng load_hex; không cần driver/sequencer. PASSIVE chỉ giữ monitor + scoreboard + coverage (và ISS nạp cùng hex). Lợi: môi trường kiểm tra giữ nguyên (cùng checker như test random), tách biệt “ai nạp chương trình” (test) khỏi “ai chấm điểm” (env). Test phải tự quản reset và objection.

Đổi sang DUT Avalon ảnh hưởng những lớp UVM nào?

Thêm: avalon_if + agent (driver đáp bus như slave RAM, monitor bus), uvm_reg adapter/predictor (Lab 13). Đổi: riscv_if (đường dẫn backdoor u_core), shadow retire (thêm mem_stall). Giữ nguyên: sequences, ISS, scoreboard so in-order, coverage ISA. Câu trả lời mạnh nhấn mạnh ranh giới ổn định (interface + retire item) giúp phần lớn TB không đổi.

Chỉ cho tôi cách bạn chứng minh TB này “thật sự bắt được lỗi”?

Mutation: danh sách lỗi cố ý (ALU +1, sai target branch, quên stall, forwarding sai, ghi lạ) × cơ chế bắt (SVA/SB/coverage); chạy regression và xác nhận mỗi lỗi bị ít nhất một cơ chế bắt. Cộng thêm factory-mutation của model (Lab 9). Nếu một lỗi không bị bắt → thiếu stimulus/checker → bổ sung. Bảng mutation là bằng chứng chất lượng TB ở cấp portfolio.
