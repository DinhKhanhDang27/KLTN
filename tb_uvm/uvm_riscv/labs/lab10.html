Tổng quan lab
  • Lab này làm gì: xây riscv_scoreboard — nhận dòng retire từ monitor (analysis port), với mỗi retire gọi ISS thực thi đúng lệnh đó và so sánh (reg_write/rd/wb_data, mem_write/addr/wdata) + kiểm luồng điều khiển (PC retire kế tiếp = PC kỳ vọng của ISS). Khớp → im lặng; lệch → UVM_ERROR chi tiết.
  • Tạo ra file nào: tb/sb/riscv_scoreboard.sv; thêm method exec(pc,instr) vào ISS (tách phần execute khỏi fetch); nối trong env.
  • Nhận gì từ lab trước: monitor + ap (Lab 4/5), ISS (Lab 9), chương trình hỗn hợp (Lab 7).
  • Lab sau dùng để làm gì: Lab 11 mở rộng so toàn kiến trúc (quét regfile+mem+pc cuối); Lab 12 cộng coverage trên cùng dòng retire.
Trọng tâm UVM của lab
  • Scoreboard là uvm_scoreboard (component) nhận transaction qua uvm_analysis_imp; vì sao cần `uvm_analysis_imp_decl khi có nhiều đầu vào.
  • imp vs uvm_tlm_analysis_fifo: đồng bộ (write) vs bất đồng bộ (get trong run_phase).
  • So sánh: compare()/do_compare, so có điều kiện, in mismatch dễ debug, ngân sách lỗi (set_max_quit_count()).
  • Kết luận PASS/FAIL: check_phase/report_phase và uvm_report_server.
  • Reset: flush queue/model; pending expected còn sót cuối test.
Mẹo tách ghép: ISS được "lái" bởi chính dòng retire — mỗi lần nhận act, scoreboard gọi exec(act.pc, act.instr). Nhờ vậy ISS KHÔNG cần ảnh chương trình; nó chỉ giữ state kiến trúc và thực thi đúng lệnh DUT đã commit. PC kỳ vọng tiếp theo dùng để bắt lỗi rẽ nhánh/nhảy.

3. Mục tiêu học

  • uvm_scoreboard + uvm_analysis_imp + hàm write().
  • So sánh từng trường có điều kiện (bỏ qua wb khi rd=0; chỉ so mem khi mem_write).
  • Kiểm luồng điều khiển: PC retire kế tiếp = PC ISS kỳ vọng.
  • Đếm match/mismatch, kết luận PASS/FAIL ở report_phase.

6. Lý thuyết ngắn — so in-order + control flow (+ UVM bên trong)

  1. In-order: pipeline commit theo thứ tự chương trình; ISS cũng tuần tự → so 1-1 theo từng retire.
  2. So có điều kiện: chỉ so wb_data khi reg_write && rd!=0 (x0 không đổi); chỉ so địa chỉ/dữ liệu store khi mem_write.
  3. Control flow: sau khi exec, ISS biết PC kỳ vọng kế. Retire kế tiếp phải có pc == exp_next → bắt lỗi branch/jal/jalr sai đích.
  4. Objection: scoreboard không cần raise; test giữ sim tới khi drain xong rồi report_phase kết luận.

6.5. Nhiều đầu vào: `uvm_analysis_imp_decl

Một class chỉ có một hàm write(T). Nếu scoreboard nhận từ hai nguồn (actual từ monitor DUT, expected từ predictor) thì uvm_analysis_imp#(T,SB) thứ hai sẽ cũng gọi write → xung đột. Macro `uvm_analysis_imp_decl(_act) sinh lớp uvm_analysis_imp_act gọi write_act(T).

`uvm_analysis_imp_decl(_act)     // đặt ở file scope (ngoài class), trong package
`uvm_analysis_imp_decl(_exp)
class riscv_sb extends uvm_scoreboard;
  uvm_analysis_imp_act #(riscv_retire_item, riscv_sb) act_imp;
  uvm_analysis_imp_exp #(riscv_retire_item, riscv_sb) exp_imp;
  function void write_act(riscv_retire_item t); … endfunction
  function void write_exp(riscv_retire_item t); … endfunction
endclass

Lab này chỉ có một đầu vào (actual) vì expected sinh ngay trong write_ret bằng ISS — nhưng tên _ret vẫn cần macro vì sau này thêm nguồn thứ hai (Lab 13).

6.7. So sánh và báo lỗi tốt

  • So có điều kiện (bỏ wb_data khi rd==0; so mem khi mem_write): đặt trong do_compare của item hoặc hàm so riêng — tránh false-fail.
  • Một thông báo lỗi = đủ để debug: PC, instr, giá trị actual/expected, số thứ tự retire. Dùng `uvm_error với ID riêng cho từng loại (REG/MEM/CF) để lọc log.
  • Lỗi dây chuyền: một lỗi đầu có thể sinh hàng trăm mismatch sau → dùng uvm_report_server::get_server().set_max_quit_count(10) hoặc dừng ở lỗi đầu tiên (+UVM_MAX_QUIT_COUNT=10).
  • Counter + trạng thái cuối: report_phase in PASS/FAIL; thử thêm check_phase kiểm không còn pending (tránh “PASS vì không so gì cả”).
Bẫy “PASS rỗng”: nếu monitor không phát retire nào (vif sai, reset kẹt) thì n_err == 0 và scoreboard báo PASS. Luôn thêm điều kiện n_cmp > 0 (hoặc ≥ số lệnh mong đợi) trong check_phase.

6.8. Thư viện có sẵn

UVM có uvm_in_order_comparator#(T) (so hai luồng in-order dùng compare()) và uvm_algorithmic_comparator (biến đổi luồng trước khi so). Hữu ích cho bài toán đơn giản; thực tế công ty thường viết scoreboard riêng vì cần so có điều kiện, báo lỗi giàu ngữ cảnh và hỗ trợ reset.

Debug: +UVM_VERBOSITY=UVM_HIGH để thấy từng “OK [n]”; thêm uvm_info theo ID SB_CMP để bật riêng; uvm_report_server::get_server().get_severity_count(UVM_ERROR) để đọc số lỗi trong report_phase.

7. Iteration 0 — scoreboard so reg/mem + pc

tb/sb/riscv_scoreboard.sv 
// tb/sb/riscv_scoreboard.sv
`ifndef RISCV_SCOREBOARD_SV
`define RISCV_SCOREBOARD_SV
`uvm_analysis_imp_decl(_ret)

class riscv_scoreboard extends uvm_scoreboard;
  `uvm_component_utils(riscv_scoreboard)

  uvm_analysis_imp_ret #(riscv_retire_item, riscv_scoreboard) ap_imp;
  riscv_ref_model iss;

  int unsigned n_cmp, n_err;
  bit          have_prev;
  bit [31:0]   exp_next_pc;

  function new(string name, uvm_component parent);
    super.new(name, parent);
    ap_imp = new("ap_imp", this);
  endfunction

  function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    iss = riscv_ref_model::type_id::create("iss");
  endfunction

  // nhận 1 retire thực tế từ monitor
  function void write_ret(riscv_retire_item act);
    riscv_retire_item exp;

    // 1) control-flow: PC retire này phải khớp PC kỳ vọng từ lần trước
    if (have_prev && act.pc !== exp_next_pc)
      `uvm_error("SB", $sformatf("CF mismatch: act.pc=0x%08h exp=0x%08h (instr=0x%08h)",
                 act.pc, exp_next_pc, act.instr))

    // 2) thực thi golden đúng lệnh DUT vừa commit
    exp = iss.exec(act.pc, act.instr);

    n_cmp++;
    // 3) so register writeback (bỏ x0)
    if (exp.reg_write && exp.rd != 0) begin
      if (act.wb_data !== exp.wb_data || act.rd !== exp.rd || !act.reg_write) begin
        n_err++;
        `uvm_error("SB", $sformatf("REG mismatch pc=0x%08h instr=0x%08h: act x%0d<=0x%08h exp x%0d<=0x%08h",
                   act.pc, act.instr, act.rd, act.wb_data, exp.rd, exp.wb_data))
      end
    end
    // 4) so store
    if (exp.mem_write) begin
      if (!act.mem_write || act.mem_addr !== exp.mem_addr || act.mem_wdata !== exp.mem_wdata) begin
        n_err++;
        `uvm_error("SB", $sformatf("MEM mismatch pc=0x%08h: act[0x%08h]<=0x%08h exp[0x%08h]<=0x%08h",
                   act.pc, act.mem_addr, act.mem_wdata, exp.mem_addr, exp.mem_wdata))
      end
    end

    exp_next_pc = iss.pc;   // ISS đã cập nhật pc trong exec
    have_prev   = 1;
    `uvm_info("SB", $sformatf("OK [%0d] %s", n_cmp, act.convert2str()), UVM_HIGH)
  endfunction

  function void report_phase(uvm_phase phase);
    if (n_err == 0)
      `uvm_info("SB", $sformatf("PASS: %0d lenh so khop, 0 loi", n_cmp), UVM_LOW)
    else
      `uvm_error("SB", $sformatf("FAIL: %0d/%0d lenh sai", n_err, n_cmp))
  endfunction
endclass
`endif

12. Phỏng vấn — hỏi & đáp

Bấm câu hỏi để xem đáp án — nên tự trả lời miệng trước khi mở. Mỗi câu có ví dụ cụ thể như khi bị hỏi trong phỏng vấn.

Vì sao cần `uvm_analysis_imp_decl? Điều gì xảy ra nếu hai uvm_analysis_imp cùng class?

Mỗi uvm_analysis_imp#(T,IMP) gọi IMP::write(T). Hai cổng cùng kiểu sẽ cùng gọi một hàm write → không phân biệt được nguồn. Macro sinh các lớp uvm_analysis_imp_act/_exp gọi write_act/write_exp riêng. Quên macro: lỗi compile “write_act not found” (hoặc dùng sai nguồn nếu bạn dùng chung write).

analysis_imp với write() hay uvm_tlm_analysis_fifo — khi nào dùng cái nào?

imp: so sánh nhanh, đồng bộ, không cần chờ (lab này). fifo: cần chờ hai luồng khớp hoặc xử lý tốn thời gian ⇒ run_phase với get(). Một scoreboard hai luồng (actual/expected) hầu như luôn dùng fifo để khỏi tự quản queue; nhược là phải xử lý phần còn lại cuối test.

task run_phase(uvm_phase phase);
  riscv_retire_item a, e;
  forever begin  act_fifo.get(a);  exp_fifo.get(e);  compare(a, e);  end
endtask
Scoreboard báo PASS nhưng test thật ra không so sánh gì. Đây là lỗi gì? Phòng thế nào?

“PASS rỗng”: monitor không phát item (vif null/reset kẹt) → n_err=0. Phòng: trong check_phase, if (n_cmp == 0) `uvm_error("SB","khong co lenh nao duoc so") hoặc so với số kỳ vọng từ driver (n_loaded). Kết hợp watchdog +UVM_TIMEOUT và coverage tối thiểu.

Một lỗi đầu tiên sinh 500 mismatch. Bạn tổ chức log thế nào để debug được?

(1) ID riêng cho từng loại (SB_REG/SB_MEM/SB_CF); (2) giới hạn: uvm_report_server::get_server().set_max_quit_count(5) hoặc +UVM_MAX_QUIT_COUNT=5,NO dừng sau vài lỗi; (3) in lỗi đầu tiên kèm ngữ cảnh 5 retire trước (giữ ring buffer trong SB) ; (4) sau lỗi đầu coi các mismatch tiếp theo là “hệ quả”, tùy chọn bỏ qua (first_error_only). Câu trả lời tốt nhấn mạnh: lỗi đầu tiên là giá trị nhất.

check_phase và report_phase dùng để làm gì? Vì sao không kết luận PASS trong run_phase?

run_phase chưa kết thúc — transaction còn có thể đến. check_phase (function, bottom-up) kiểm điều kiện “cuối test”: queue rỗng, đã so đủ số lượng. report_phase in tóm tắt. Thực hành: kiểm trong check_phase (dùng uvm_error), in trong report_phase → bộ đếm lỗi đã đủ trước khi in.

Scoreboard xử lý reset như thế nào?

Khi DUT reset: xóa queue expected, iss.reset(), đặt have_prev=0. Tín hiệu reset đến từ đâu? monitor phát “reset item”/uvm_event, hoặc scoreboard lắng nghe analysis riêng. Quên → mismatch giả ở chương trình tiếp theo. Cân nhắc: transaction đang bay lúc reset phải bị loại (flush) chứ không được coi là lỗi.

compare() tự động (field macros) hay viết tay do_compare — scoreboard này chọn gì và vì sao?

Viết tay trong scoreboard: cần so có điều kiện (wb_data chỉ khi rd!=0), cần thông điệp giàu ngữ cảnh, và hiệu năng. item.compare() với field macros so mọi field, sẽ báo lỗi giả với wb_data của jal x0. Nếu vẫn muốn dùng compare(), đặt logic có điều kiện vào do_compare của riscv_retire_item.

Scoreboard có nên raise objection không? Khi nào?

Thường không; test lo kết thúc. Nhưng khi scoreboard xử lý bất đồng bộ (fifo) và còn expected chưa so khi test drop objection, kết quả bị cắt. Giải pháp: test dùng drain_time, hoặc scoreboard raise objection khi còn pending và drop khi rỗng (hoặc dùng phase_ready_to_end để trì hoãn kết thúc cho đến khi fifo rỗng).

14. Bài tập code & câu hỏi nâng cao UVM

8 bài rèn tay, tăng dần độ khó. Làm trên baseline của lab này; đáp án chỉ là hướng tham khảo — giá trị nằm ở việc bạn tự gõ, chạy và đọc log.

0 / 8 bài đã làm
★ Dễ

EX1 — Thêm ID lỗi theo loại

Tách `uvm_error("SB", …) thành SB_REG, SB_MEM, SB_CF. Dùng +uvm_set_severity hoặc set_report_severity_id_override hạ SB_CF xuống WARNING cho một test thử nghiệm.
Gợi ý & đáp án tham khảo

set_report_severity_id_override(UVM_ERROR, "SB_CF", UVM_WARNING) — công cụ dùng trong negative test khi một loại lỗi được biết trước.

★ Dễ

EX2 — Chống PASS rỗng

Thêm check_phase: lỗi nếu n_cmp == 0. Cố ý tắt monitor (không phát) và chạy.
Gợi ý & đáp án tham khảo

Không có guard, báo cáo là PASS! Đây là lỗi “xanh giả” kinh điển.

★★ Vừa

EX3 — Scoreboard dùng analysis fifo

Chuyển write_ret thành uvm_tlm_analysis_fifo + run_phase forever get. In act_fifo.used() tại check_phase; kiểm tra rỗng.
Gợi ý & đáp án tham khảo

Chú ý kết thúc test: nếu test drop objection trước khi fifo rỗng, một số retire không được so. Thêm phase_ready_to_end hoặc drain_time.

★★ Vừa

EX4 — Giới hạn lỗi

Chạy bản cố ý sai ALU (+1). Dùng +UVM_MAX_QUIT_COUNT=3,NO và quan sát. Viết một bình luận 3 dòng: tại sao lỗi đầu tiên là đáng giá nhất.
Gợi ý & đáp án tham khảo

Sau 3 lỗi UVM gọi die() (kết thúc sớm). Với NO nghĩa là không overridable ở runtime.

★★ Vừa

EX5 — Ring buffer ngữ cảnh

Giữ 5 retire gần nhất trong queue. Khi có mismatch in thêm 5 retire đó. So với log chỉ có dòng lỗi.
Gợi ý & đáp án tham khảo

Dùng riscv_retire_item hist[$]; if (hist.size()>5) void'(hist.pop_front()); Ngữ cảnh gần giúp thấy ngay lệnh trước (forwarding?) gây lỗi.

★★ Vừa

EX6 — Two-stream scoreboard

Tách ISS thành predictor (Lab 9 EX3) phát expected; scoreboard dùng hai analysis_imp_decl (_act, _exp) và queue. Xử lý trường hợp expected đến trước/sau actual.
Gợi ý & đáp án tham khảo

Cần hai queue + hàm try_match() gọi ở cả hai write_*. Cuối test báo phần tử thừa ở queue nào — thông tin chẩn đoán rất hữu ích (thiếu actual = DUT mất lệnh; thiếu expected = DUT thừa).

★★★ Khó

EX7 — Bắt lỗi bằng factory-mutation

Dùng model lỗi (Lab 9 EX1) cho 5 lỗi khác nhau; lập bảng lỗi nào được bắt bởi nhóm so sánh nào (REG/MEM/CF).
Gợi ý & đáp án tham khảo

Lỗi branch condition → CF; SW địa chỉ → MEM; ALU → REG. Một nhóm nào không bao giờ bắt được lỗi nào? → nhóm đó thừa hoặc thiếu stimulus.

★★★ Khó

EX8 — Dùng uvm_in_order_comparator

Thay scoreboard tay bằng uvm_in_order_comparator#(riscv_retire_item): predictor nối before_export, monitor nối after_export. Cần do_compare trong item. So sánh khả năng báo lỗi.
Gợi ý & đáp án tham khảo

Nhận xét điển hình: dùng nhanh, nhưng thông điệp lỗi chung chung, không so có điều kiện được trừ khi do_compare làm; khó xử lý reset. Vì vậy công ty thường viết riêng.
