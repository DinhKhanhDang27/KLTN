Tổng quan lab
  • Lab này làm gì: xây riscv_monitor — mỗi chu kỳ sample ret_cb; khi ret_valid=1 dựng một transaction retire (riscv_retire_item: pc, instr, rd, wb_data, mem…) và phát qua uvm_analysis_port. Đây là "dòng commit" in-order mà scoreboard/coverage sẽ tiêu thụ.
  • Tạo ra file nào: tb/agent/riscv_retire_item.sv (transaction quan sát), tb/agent/riscv_monitor.sv, và top thử riscv_mon_tb.sv (driver + monitor + 1 subscriber in ra).
  • Nhận gì từ lab trước: interface có cổng retire (Lab 1), driver (Lab 3), seq_item (Lab 2).
  • Lab sau dùng để làm gì: Lab 5 gói vào agent; Lab 10 nối analysis port vào scoreboard; Lab 12 nối vào coverage subscriber.
Trọng tâm UVM của lab
  • TLM-1 analysis: uvm_analysis_port → export → imp; write() là function không block, 1→N.
  • Monitor thụ động: tách khỏi driver, chạy được ở agent PASSIVE; dựng observed item từ tín hiệu.
  • Handle sharing: analysis port không clone — subscriber nhận cùng một object. Quy tắc “tạo item mới mỗi giao dịch”.
  • Reporting: uvm_info và verbosity là công cụ debug thật; chi phí khi để ở UVM_HIGH.
  • Retire stream đã in-order nhờ shadow pipeline (Lab 1) — monitor chỉ cần lọc ret_valid.
Khác single-cycle: monitor single-cycle sample mỗi posedge và luôn có 1 lệnh. Monitor pipeline chỉ phát transaction khi ret_valid=1 — bỏ qua các chu kỳ bubble/flush. Nhờ shadow pipeline (Lab 1), dòng transaction đã đúng thứ tự chương trình.

3. Mục tiêu học

  • uvm_monitor + uvm_analysis_port #(riscv_retire_item) + write().
  • Sample đồng bộ qua clocking block, lọc ret_valid.
  • Thiết kế transaction quan sát riêng (tách khỏi stimulus item) — chỉ chứa thứ "nhìn thấy".
  • Broadcast 1→nhiều: analysis port gửi tới mọi subscriber đã connect.

6. Lý thuyết ngắn — sample + analysis (+ TLM bên trong)

  1. Transaction quan sát riêng: stimulus item (Lab 2) mô tả "muốn gửi gì"; retire item mô tả "DUT đã làm gì". Tách biệt giúp scoreboard so kỳ vọng (từ ISS) với thực tế (từ monitor).
  2. Lọc valid: chỉ khi ret_valid mới tạo transaction. Các chu kỳ bubble/flush bị bỏ qua tự nhiên.
  3. Analysis port broadcast: một write() tới tất cả subscriber — 0, 1 hay N; không block. Monitor không cần biết ai nghe.
  4. Thụ động: monitor không bao giờ lái tín hiệu — chỉ đọc. Dùng modport mon.

6.5. Ba loại cổng analysis và quy tắc kết nối

CổngVai tròVí dụ
uvm_analysis_port#(T)Nguồn phát (monitor)ap.write(tr);
uvm_analysis_export#(T)Cổng “chuyển tiếp” qua ranh giới hierarchy (không có logic)agent.ap nối tới mon.ap
uvm_analysis_imp#(T,IMP)Điểm cuối: gọi IMP::write(T)scoreboard, subscriber

Quy tắc: port → export → imp (từ nguồn tới đích); connect_phase gọi source.connect(sink). Một port nối được tới nhiều sink — mỗi write() gọi lần lượt tất cả (broadcast, không có thứ tự đảm bảo giữa các sink).

// agent chuyển tiếp ap của monitor ra ngoài (pattern chuẩn)
uvm_analysis_port#(riscv_retire_item) ap;                // trong agent
function void connect_phase(uvm_phase phase);
  mon.ap.connect(this.ap);                              // port → port: được phép (cấp trên là "cổng chuyển tiếp")
endfunction
// env: agent.ap.connect(sb.ap_imp);  agent.ap.connect(cov.analysis_export);

6.6. write() là function — hệ quả

  • Không được tiêu thời gian trong write() (không #delay, không @event). Cần xử lý chậm → đẩy vào uvm_tlm_analysis_fifo rồi xử lý ở run_phase (Lab 10).
  • Không có back-pressure: monitor không biết subscriber nhận xong chưa; nó phát rồi đi tiếp.
  • Cùng một handle: tất cả subscriber thấy cùng object. Subscriber sửa item → làm hỏng người khác. Quy ước: item từ analysis port là read-only; cần giữ lâu thì clone().
Bẫy: monitor khai báo riscv_retire_item tr; ở cấp class, tạo một lần rồi sửa field mỗi chu kỳ → scoreboard lưu handle vào queue sẽ thấy mọi phần tử giống nhau (đều là trạng thái mới nhất). Luôn create trong vòng lặp (như code lab).

6.7. Monitor trong kiến trúc UVM

  • Thụ động tuyệt đối: chỉ đọc qua clocking block; chạy ở cả agent ACTIVE lẫn PASSIVE.
  • Một monitor = một góc nhìn: nếu cần cả “ý định nạp” lẫn “kết quả retire”, dùng hai monitor/ hai analysis port, đừng nhồi vào một.
  • Đặt ap ở đâu? ap = new("ap", this) trong new() (như lab) hoặc build_phase — cả hai đúng; UVM style hiện đại ưu tiên build_phase để tương thích config.
  • Checker trong monitor? Kiểm giao thức nhẹ thì được; so sánh giá trị thì thuộc scoreboard (Lab 10).
Debug: +UVM_VERBOSITY=UVM_MEDIUM để thấy từng retire; uvm_top.print_topology() kiểm tra analysis port đã gắn đúng; +uvm_set_verbosity=*mon*,_ALL_,UVM_HIGH,run chỉ bật chi tiết cho monitor.

// tb/agent/riscv_retire_item.sv — bản ghi 1 lệnh đã commit (quan sát)
`ifndef RISCV_RETIRE_ITEM_SV
`define RISCV_RETIRE_ITEM_SV

class riscv_retire_item extends uvm_sequence_item;
  bit [31:0] pc;
  bit [31:0] instr;
  bit        reg_write;
  bit [4:0]  rd;
  bit [31:0] wb_data;
  bit        mem_write;
  bit [31:0] mem_addr;
  bit [31:0] mem_wdata;

  `uvm_object_utils_begin(riscv_retire_item)
    `uvm_field_int(pc,        UVM_ALL_ON | UVM_HEX)
    `uvm_field_int(instr,     UVM_ALL_ON | UVM_HEX)
    `uvm_field_int(reg_write, UVM_ALL_ON)
    `uvm_field_int(rd,        UVM_ALL_ON)
    `uvm_field_int(wb_data,   UVM_ALL_ON | UVM_HEX)
    `uvm_field_int(mem_write, UVM_ALL_ON)
    `uvm_field_int(mem_addr,  UVM_ALL_ON | UVM_HEX)
    `uvm_field_int(mem_wdata, UVM_ALL_ON | UVM_HEX)
  `uvm_object_utils_end

  function new(string name="riscv_retire_item"); super.new(name); endfunction

  function string convert2str();
    return $sformatf("pc=0x%08h instr=0x%08h %s %s", pc, instr,
      reg_write ? $sformatf("x%0d<=0x%08h", rd, wb_data) : "(no-regwr)",
      mem_write ? $sformatf("MEM[0x%08h]<=0x%08h", mem_addr, mem_wdata) : "");
  endfunction
endclass
`endif

// tb/agent/riscv_monitor.sv
`ifndef RISCV_MONITOR_SV
`define RISCV_MONITOR_SV

class riscv_monitor extends uvm_monitor;
  `uvm_component_utils(riscv_monitor)

  virtual riscv_if vif;
  uvm_analysis_port #(riscv_retire_item) ap;
  int unsigned retire_count;

  function new(string name, uvm_component parent);
    super.new(name, parent);
    ap = new("ap", this);
  endfunction

  function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    if (!uvm_config_db#(virtual riscv_if)::get(this, "", "vif", vif))
      `uvm_fatal("MON", "Khong lay duoc vif")
  endfunction

  task run_phase(uvm_phase phase);
    forever begin
      @(vif.ret_cb);
      if (vif.ret_cb.ret_valid) begin
        riscv_retire_item tr = riscv_retire_item::type_id::create("tr");
        tr.pc        = vif.ret_cb.ret_pc;
        tr.instr     = vif.ret_cb.ret_instr;
        tr.reg_write = vif.ret_cb.ret_reg_write;
        tr.rd        = vif.ret_cb.ret_rd;
        tr.wb_data   = vif.ret_cb.ret_wb_data;
        tr.mem_write = vif.ret_cb.ret_mem_write;
        tr.mem_addr  = vif.ret_cb.ret_mem_addr;
        tr.mem_wdata = vif.ret_cb.ret_mem_wdata;
        retire_count++;
        `uvm_info("MON", $sformatf("[%0d] %s", retire_count, tr.convert2str()), UVM_MEDIUM)
        ap.write(tr);
      end
    end
  endtask

  function void report_phase(uvm_phase phase);
    `uvm_info("MON", $sformatf("Tong so lenh retire = %0d", retire_count), UVM_LOW)
  endfunction
endclass
`endif

// tb/top/riscv_mon_tb.sv
`timescale 1ns/1ps
module riscv_mon_tb;
  import uvm_pkg::*; `include "uvm_macros.svh"
  `include "riscv_seq_item.sv"
  `include "riscv_retire_item.sv"
  `include "riscv_driver.sv"
  `include "riscv_monitor.sv"

  logic clk = 0; always #5 clk = ~clk;
  riscv_if vif (.clk(clk));
  riscv_pipeline_top dut (.clk(clk), .rst(vif.rst), .out_pc(), .out_alu_result());

  // ---- probe + shadow pipeline từ Lab 1 (bắt buộc để có ret_* đúng) ----
  assign vif.pc_if=dut.pc_if; assign vif.alu_result_ex=dut.alu_result_ex;
  assign vif.stall=dut.stall; assign vif.redirect=dut.redirect;
  logic s_idex_valid,s_exmem_valid,s_memwb_valid;
  logic [31:0] s_idex_pc,s_exmem_pc,s_memwb_pc,s_idex_instr,s_exmem_instr,s_memwb_instr;
  logic s_memwb_mwrite; logic [31:0] s_memwb_maddr,s_memwb_mwdata;
  always @(posedge clk or posedge vif.rst) if(vif.rst) begin
    s_idex_valid<=0; s_exmem_valid<=0; s_memwb_valid<=0;
  end else begin
    s_idex_valid<=(dut.redirect|dut.stall)?1'b0:dut.ifid_valid;
    s_idex_pc<=dut.ifid_pc; s_idex_instr<=dut.ifid_instr;
    s_exmem_valid<=s_idex_valid; s_exmem_pc<=s_idex_pc; s_exmem_instr<=s_idex_instr;
    s_memwb_valid<=s_exmem_valid; s_memwb_pc<=s_exmem_pc; s_memwb_instr<=s_exmem_instr;
    s_memwb_mwrite<=dut.exmem_mem_write; s_memwb_maddr<=dut.exmem_alu_result; s_memwb_mwdata<=dut.exmem_store_data;
  end
  assign vif.ret_valid=s_memwb_valid; assign vif.ret_pc=s_memwb_pc; assign vif.ret_instr=s_memwb_instr;
  assign vif.ret_reg_write=dut.memwb_reg_write_r; assign vif.ret_rd=dut.memwb_rd_r; assign vif.ret_wb_data=dut.memwb_wb_value_r;
  assign vif.ret_mem_write=s_memwb_mwrite; assign vif.ret_mem_addr=s_memwb_maddr; assign vif.ret_mem_wdata=s_memwb_mwdata;

  typedef uvm_sequencer #(riscv_seq_item) riscv_sequencer;

  // subscriber in ra mỗi transaction
  class print_sub extends uvm_subscriber #(riscv_retire_item);
    `uvm_component_utils(print_sub)
    function new(string n, uvm_component p); super.new(n,p); endfunction
    function void write(riscv_retire_item t);
      `uvm_info("SUB", $sformatf("nhan: %s", t.convert2str()), UVM_LOW)
    endfunction
  endclass

  class prog_seq extends uvm_sequence #(riscv_seq_item);
    `uvm_object_utils(prog_seq)
    function new(string name="prog_seq"); super.new(name); endfunction
    task body();
      bit [31:0] words[] = '{32'h00500093,32'h00308113,32'h002081b3,32'h00302023,32'h0000006f};
      foreach(words[i]) begin
        riscv_seq_item it = riscv_seq_item::type_id::create($sformatf("it%0d",i));
        start_item(it); void'(it.randomize());
        it.raw_word=words[i]; it.use_raw=1; it.last_instr=(i==words.size()-1);
        finish_item(it);
      end
    endtask
  endclass

  class mon_test extends uvm_test;
    `uvm_component_utils(mon_test)
    riscv_driver drv; riscv_monitor mon; riscv_sequencer sqr; print_sub sub;
    function new(string n, uvm_component p); super.new(n,p); endfunction
    function void build_phase(uvm_phase phase);
      drv=riscv_driver::type_id::create("drv",this);
      mon=riscv_monitor::type_id::create("mon",this);
      sqr=riscv_sequencer::type_id::create("sqr",this);
      sub=print_sub::type_id::create("sub",this);
      uvm_config_db#(virtual riscv_if)::set(this,"drv","vif",vif);
      uvm_config_db#(virtual riscv_if)::set(this,"mon","vif",vif);
    endfunction
    function void connect_phase(uvm_phase phase);
      drv.seq_item_port.connect(sqr.seq_item_export);
      mon.ap.connect(sub.analysis_export);
    endfunction
    task run_phase(uvm_phase phase);
      prog_seq seq = prog_seq::type_id::create("seq");
      phase.raise_objection(this);
      seq.start(sqr);
      repeat (25) @(posedge clk);
      phase.drop_objection(this);
    endtask
  endclass

  initial run_test("mon_test");
endmodule

8. Iterations

Iteration 1 — nối 2 subscriber (broadcast)

Tạo thêm count_sub chỉ đếm; connect cả hai vào mon.ap.

Khác biệt

Một write() tới cả 2. Dạy: analysis port là 1→N, thêm người nghe không sửa monitor.

Iteration 2 — sample sai: bỏ clocking, đọc thẳng vif.ret_valid ở posedge

Đổi @(vif.ret_cb); vif.ret_cb.ret_valid → @(posedge vif.clk); vif.ret_valid.

Khác biệt

Có thể bắt giá trị đang chuyển (race), đôi khi lệch 1 chu kỳ hoặc dính giá trị trung gian. Dạy: luôn sample qua clocking.

Iteration 3 — chương trình có branch taken (kiểm flush không lọt)

Dùng chương trình Iteration 3 của Lab 1 (beq taken + lệnh bị flush).

Khác biệt

Lệnh bị flush KHÔNG xuất hiện trong dòng monitor (không có transaction). Dạy: monitor phản ánh đúng commit, không phải fetch.

Iteration 4 — in bằng tr.print() (field macro)

Trong subscriber gọi t.print().

Khác biệt

Bảng field tự sinh (pc/instr/rd...). Dạy: field macros phục vụ cả monitor transaction.

Iteration 5 — thêm trường cycle (số chu kỳ từ nhả reset)

Monitor đếm chu kỳ, gán tr.cycle.

Khác biệt

Thấy độ trễ pipeline (lệnh 1 retire ở cycle ~5). Dạy: timestamp giúp debug thứ tự/độ trễ.

12. Phỏng vấn — hỏi & đáp

Bấm câu hỏi để xem đáp án — nên tự trả lời miệng trước khi mở. Mỗi câu có ví dụ cụ thể như khi bị hỏi trong phỏng vấn.

Analysis port khác put/get port của TLM ở điểm nào? Vì sao monitor dùng analysis?

put/get: 1→1, có thể block (task), có back-pressure; producer biết consumer nhận. Analysis: 1→N, function không block, fire-and-forget. Monitor không được phép làm chậm DUT/TB và không nên biết ai nghe (scoreboard, coverage, logger…) → broadcast không block là hợp lý.

ap.write(tr);                       // monitor — không biết có bao nhiêu subscriber
// env: agent.ap.connect(sb.ap_imp);  agent.ap.connect(cov.analysis_export);  agent.ap.connect(logger.analysis_export);
write() có thể chứa #10 hoặc @(posedge clk) không? Nếu scoreboard cần xử lý chậm thì làm gì?

Không: write() là function (zero-time) — compile lỗi nếu có delay. Với xử lý chậm, dùng uvm_tlm_analysis_fifo: write() chỉ nhét vào fifo (zero-time), còn run_phase của scoreboard fifo.get(item) (task, block được) rồi xử lý theo ý.

uvm_tlm_analysis_fifo#(riscv_retire_item) act_fifo;
task run_phase(uvm_phase phase);
  riscv_retire_item act;
  forever begin act_fifo.get(act);  compare(act);  end
endtask
Hai subscriber cùng nhận một item từ write(). Một cái sửa item.pc. Chuyện gì xảy ra?

Cả hai nhận cùng handle nên subscriber còn lại thấy pc bị sửa — và thứ tự gọi write giữa các subscriber không đảm bảo → lỗi không tái hiện ổn định. Cách phòng: coi item là read-only; nếu cần biến đổi thì clone() trước ($cast(my, t.clone())).

Vì sao monitor tạo riscv_retire_item mới cho mỗi retire thay vì dùng lại một biến?

Vì handle được chia sẻ. Scoreboard thường queue.push_back(t) (lưu handle); nếu monitor sửa lại cùng object ở chu kỳ sau, toàn bộ queue trỏ vào một object duy nhất mang dữ liệu mới nhất. type_id::create mỗi giao dịch tốn bộ nhớ nhưng an toàn; garbage collector thu hồi khi không còn tham chiếu.

Monitor sample qua clocking block hay trực tiếp? Cho ví dụ lỗi nếu làm sai.

Qua clocking block với default input #1step (Preponed → giá trị ổn định). Lấy trực tiếp ở @(posedge clk) có thể thấy giá trị trước hoặc sau NBA của RTL → 1 retire đôi khi bị bỏ sót hoặc đếm đúp (Iteration 2). Dấu hiệu: số lệnh retire khác nhau giữa các simulator/seed dù chương trình giống nhau.

Agent PASSIVE khác ACTIVE ở monitor không? Vì sao monitor phải chạy ở cả hai?

Không khác. Monitor luôn được tạo; PASSIVE chỉ bỏ driver + sequencer. Dùng PASSIVE khi stimulus đến từ nguồn khác (firmware thật nạp bằng load_hex ở Lab 15, hoặc agent khác lái bus) mà ta vẫn muốn quan sát và chấm điểm. Monitor độc lập với driver nên scoreboard/coverage hoạt động như nhau.

Nên đặt coverage/checker vào monitor hay tách thành subscriber? Lý do?

Tách. Monitor chỉ “dịch tín hiệu → transaction”. Coverage và scoreboard là subscriber: (1) bật/tắt bằng config mà không đụng monitor, (2) tái dùng monitor cho dự án khác, (3) mỗi thành phần một trách nhiệm → dễ debug. Ngoại lệ: kiểm tra giao thức tức thời cực nhẹ (ví dụ $isunknown) đôi khi đặt trong monitor, nhưng assertion trong interface vẫn gọn hơn.

Làm sao chỉ bật log chi tiết cho riêng monitor mà không làm ngập log toàn bộ?

Dùng verbosity theo hierarchy: command line +uvm_set_verbosity=uvm_test_top.env.agent.mon,_ALL_,UVM_HIGH,run hoặc trong code mon.set_report_verbosity_level(UVM_HIGH) / set_report_verbosity_level_hier. Với ID: set_report_id_verbosity("MON", UVM_HIGH). Quan trọng: `uvm_info không đánh giá đối số khi verbosity thấp hơn mức yêu cầu nên để dòng log chi tiết trong hot path không tốn thêm khi tắt.

class riscv_monitor extends uvm_monitor;
  uvm_analysis_port#(riscv_retire_item) ap;  // new("ap",this)
  run: forever begin @(vif.ret_cb);
         if(vif.ret_cb.ret_valid) begin
           tr=riscv_retire_item::type_id::create("tr");
           tr.pc=ret_cb.ret_pc; tr.rd=ret_cb.ret_rd; ...; ap.write(tr); end end
