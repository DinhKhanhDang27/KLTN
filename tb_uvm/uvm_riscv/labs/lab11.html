Trọng tâm UVM của lab
  • Phase cuối test: extract_phase (thu thập) → check_phase (kiểm) → report_phase (in); vì sao sweep không nên nằm rải rác trong run_phase của test.
  • Hai lớp kiểm: per-transaction (định vị) + end-of-state (lưới an toàn) — tư duy thiết kế checker.
  • Kiến trúc backdoor: scoreboard cầm vif để peek — tiện nhưng gắn cứng; giải pháp trừu tượng hóa.
  • Đồng bộ test ↔ scoreboard: uvm_event, phase_ready_to_end, objection khi còn pending.
  • Ngân sách lỗi & báo cáo: uvm_report_server, đếm severity, kết luận một dòng.
Hai lớp kiểm: (1) per-retire — bắt lỗi ngay tại lệnh, định vị chính xác. (2) end-of-state sweep — mạng lưới an toàn: nếu per-retire bỏ sót (vd ghi đè regfile ngoài dòng retire), sweep cuối vẫn lộ. Hai lớp cộng lại ≈ self-checking đầy đủ.

6. Lý thuyết ngắn — sweep toàn kiến trúc (+ UVM bên trong)

  1. Vì sao cần sweep? Dòng retire chỉ phản ánh "ghi do lệnh commit". Nếu có đường ghi lạ (bug) hoặc byte memory sai do store sai độ rộng, sweep so toàn bộ mới chắc.
  2. Quét đúng chỗ: regfile chỉ 32 ô → quét hết. Memory thưa → quét các word ISS từng ghi (keys của dmem), căn chỉnh 4.
  3. PC cuối: sau drain, DUT dừng ở jal x0,0 (loop) → PC = địa chỉ halt. ISS cũng dừng tại đó (nextpc = pc). So PC cuối.
  4. Random dài: vseq sinh ~30 lệnh hỗn hợp; không cần tính tay — ISS là đáp án.

6.5. Sweep nên ở phase nào?

Bản lab gọi env.sb.final_check() từ run_phase của test sau khi chờ drain. Cách này chạy được nhưng gắn kiểm tra vào từng test (mỗi test phải nhớ gọi). Cách chuẩn: scoreboard tự sweep trong check_phase (hoặc extract_phase thu thập rồi check_phase so):

function void extract_phase(uvm_phase phase);      // thu thập state DUT
  for (int r = 1; r < 32; r++) dut_reg[r] = vif.peek_reg(r);
endfunction
function void check_phase(uvm_phase phase);        // so với model, báo lỗi
  for (int r = 1; r < 32; r++)
    if (dut_reg[r] !== iss.xreg[r]) `uvm_error("REGSWEEP", …)
  if (n_cmp == 0) `uvm_error("SB", "khong co lenh nao duoc so")
endfunction

Hai điều kiện để làm vậy: (1) mọi transaction cuối cùng đã đến scoreboard trước khi run_phase kết thúc (drain đủ, hoặc phase_ready_to_end); (2) check_phase là function — dùng được backdoor peek (function, zero-time), không dùng @.

6.6. Trì hoãn kết thúc bằng phase_ready_to_end

Khi objection về 0, UVM gọi phase_ready_to_end(run_phase) trên mọi component trước khi thực sự kết thúc. Component có thể raise objection ngược lại để xin thêm thời gian — cách sạch để “chờ pending = 0” mà không hard-code số chu kỳ drain:

virtual function void phase_ready_to_end(uvm_phase phase);
  if (phase.get_name() != "run") return;
  if (pending_count() != 0) begin
    phase.raise_objection(this, "SB con pending");
    fork begin  wait (pending_count() == 0);  phase.drop_objection(this);  end join_none
  end
endfunction

6.7. Ai được “biết” DUT? Backdoor trong scoreboard

Scoreboard cầm virtual riscv_if để gọi peek_reg/peek_mem là tiện, nhưng buộc scoreboard vào interface này. Hai cải tiến phổ biến: (1) interface “backdoor” trừu tượng — một virtual class riscv_state_peek với peek_reg/peek_mem, nhiều hiện thực (RTL path / DPI / SW model) đặt trong config object; (2) dùng RAL uvm_reg/uvm_mem backdoor (Lab 13) — scoreboard hỏi register model, không biết đường dẫn RTL.

Bẫy thời điểm: peek ở check_phase sau khi run_phase kết thúc: nếu test dừng đột ngột (timeout) thì DUT có thể đang giữa chương trình → sweep báo lỗi giả. Chỉ sweep khi “đã halt” (cờ do driver/test báo).

6.8. Thống kê & kết luận qua report server

function void report_phase(uvm_phase phase);
  uvm_report_server srv = uvm_report_server::get_server();
  int unsigned e = srv.get_severity_count(UVM_ERROR);
  int unsigned f = srv.get_severity_count(UVM_FATAL);
  `uvm_info("RESULT", $sformatf("%s  (cmp=%0d err=%0d fatal=%0d)", (e+f==0 && n_cmp>0) ? "** TEST PASSED **" : "** TEST FAILED **", n_cmp, e, f), UVM_NONE)
endfunction

Một dòng cố định (TEST PASSED/FAILED) giúp script regression grep ổn định (Lab 15).

7. Iteration 0 — final_check sweep

Nâng cấp tb/sb/riscv_scoreboard.sv (phần thêm) 
// thêm vào riscv_scoreboard:
  virtual riscv_if vif;
  bit [31:0] last_pc;         // PC lệnh retire cuối

  // trong build_phase:
  if (!uvm_config_db#(virtual riscv_if)::get(this,"","vif",vif))
    `uvm_fatal("SB","thieu vif");

  // trong write_ret(): sau khi exec, nhớ PC cuối:
  last_pc = act.pc;

  // sweep toàn kiến trúc — test gọi sau khi drain xong
  function void final_check();
    int errs = 0;
    // 1) regfile x1..x31
    for (int r = 1; r < 32; r++) begin
      bit [31:0] d = vif.peek_reg(r);
      if (d !== iss.xreg[r]) begin
        errs++;
        `uvm_error("SB", $sformatf("REGSWEEP x%0d: dut=0x%08h iss=0x%08h", r, d, iss.xreg[r]))
      end
    end
    // 2) data memory: quét các word ISS đã ghi
    begin
      bit seen[int];   // tránh quét trùng word
      foreach (iss.dmem[a]) begin
        int w = a & ~3;
        if (!seen.exists(w)) begin
          bit [31:0] dm = vif.peek_mem(w);
          bit [31:0] im = iss.ld_w(w);
          seen[w] = 1;
          if (dm !== im) begin
            errs++;
            `uvm_error("SB", $sformatf("MEMSWEEP[0x%08h]: dut=0x%08h iss=0x%08h", w, dm, im))
          end
        end
      end
    end
    // 3) PC cuối (xấp xỉ: PC retire cuối == pc ISS tại lệnh cuối)
    //    (đầy đủ hơn: probe out_pc so iss.pc — xem iteration 3)
    if (errs == 0)
      `uvm_info("SB", $sformatf("SWEEP PASS: regfile+mem khop (retire=%0d)", n_cmp), UVM_LOW)
    else
      `uvm_error("SB", $sformatf("SWEEP FAIL: %0d sai", errs))
  endfunction

Test gọi sweep + chương trình random dài (self_check_test) 
`ifndef SELF_CHECK_TEST_SV
`define SELF_CHECK_TEST_SV
class self_check_test extends riscv_base_test;
  `uvm_component_utils(self_check_test)
  function new(string n,uvm_component p); super.new(n,p); endfunction
  // (KHÔNG cần set vif ở test — env đã set cho sb, xem snippet "Nâng cấp env" bên dưới)
  task run_phase(uvm_phase phase);
    riscv_vseq v = riscv_vseq::type_id::create("v");
    phase.raise_objection(this);
    v.start(env.vsqr);
    repeat (60) @(posedge cfg.vif.clk);   // drain dư cho chương trình dài
    env.sb.final_check();                 // sweep cuối
    phase.drop_objection(this);
  endtask
endclass
`endif

8. Iterations

Iteration 1 — bơm lỗi store độ rộng (data_memory) → chỉ sweep bắt

Tạm sửa data_memory.sv ghi thiếu 1 byte (bỏ byte[31:24]).

Khác biệt

Dòng retire vẫn "store đúng ý định" (monitor lấy wdata từ DUT port), nhưng MEMSWEEP so nội dung thực tế → lộ byte sai. Dạy: sweep bắt lỗi lưu trữ mà per-retire bỏ sót. Hoàn tác sau.

Iteration 2 — chương trình SW rồi LW khác word (địa chỉ phân tán)

vseq sinh nhiều SW ở địa chỉ khác nhau.

Khác biệt

Sweep quét nhiều word; dmem keys phân tán. Dạy: assoc array + seen[] tránh quét trùng.

Iteration 3 — so PC cuối bằng probe out_pc

Thêm probe vif.out_pc (nối dut.out_pc); so vif.out_pc == iss.pc trong sweep.

Khác biệt

Kiểm PC dừng khớp. Dạy: hoàn tất bộ ba regfile+mem+pc.

Iteration 4 — random 5 seed liên tiếp (self-check lặp)

Chạy vseq 5 lần (reset giữa mỗi lần), sweep sau mỗi lần.

Khác biệt

Mỗi seed một chương trình khác, đều PASS. Dạy: self-check mở đường cho regression Lab 15.

Iteration 5 — bật quét toàn bộ 2048 byte (chậm) để so sánh hiệu năng

Thay quét theo keys bằng vòng 0..2047 step 4.

Khác biệt

Chậm hơn nhiều, kết quả như nhau. Dạy: quét theo keys đã ghi là tối ưu; quét toàn bộ chỉ khi nghi ghi lạ.

12. Phỏng vấn — hỏi & đáp

Bấm câu hỏi để xem đáp án — nên tự trả lời miệng trước khi mở. Mỗi câu có ví dụ cụ thể như khi bị hỏi trong phỏng vấn.

Vì sao quét state cuối cùng khi đã có so sánh từng retire? Cho ví dụ lỗi chỉ lộ ở sweep.

Per-retire so dữ liệu monitor thấy (ý định ghi), không phải nội dung thật trong bộ nhớ/regfile. Ví dụ: data_memory RTL bỏ mất byte[31:24] khi ghi: monitor vẫn thấy mem_wdata đầy đủ ở cổng retire → per-retire OK; nhưng peek_mem cho giá trị thiếu byte ⇒ MEMSWEEP báo lỗi. Triết lý: hai lớp kiểm khác quan điểm thì bổ trợ nhau.

Nên sweep ở run_phase của test hay check_phase của scoreboard?

check_phase của scoreboard: đóng gói trong component, mọi test tự hưởng, chạy đúng lúc “mọi thứ đã xong”. Sweep trong test dễ bị quên và phụ thuộc thời gian chờ cố định. Điều kiện: dữ liệu đã đủ khi run_phase kết thúc (dùng drain_time/phase_ready_to_end), và chỉ dùng function (peek) trong check_phase.

phase_ready_to_end là gì? Khi nào dùng?

Callback được gọi khi objection của một phase về 0, trước khi phase thực sự kết thúc; component có thể raise objection mới để trì hoãn. Dùng khi “không biết trước phải chờ bao lâu” (còn pending trong fifo, đợi response cuối). Thay cho #delay cứng — vừa chính xác vừa không lãng phí thời gian mô phỏng.

uvm_event dùng để làm gì giữa test và scoreboard? Khác @(posedge) thế nào?

uvm_event là đối tượng đồng bộ hóa có tên, có thể mang dữ liệu (trigger(data)/wait_trigger_data), tra theo tên qua uvm_event_pool::get_global("halt_done") nên hai component không cần biết nhau. Ví dụ: driver trigger "prog_done" khi đã drain; scoreboard wait_trigger rồi sweep. Khác @(posedge clk): không gắn clock, rút gọn phụ thuộc giữa component.

uvm_event ev = uvm_event_pool::get_global("prog_done");
// driver:      ev.trigger();
// scoreboard:  ev.wait_trigger();  sweep();
Scoreboard cầm virtual riscv_if để peek DUT — điểm yếu và cách cải thiện?

Yếu: gắn cứng scoreboard vào interface cụ thể + đường dẫn RTL; đổi DUT (Lab 15 Avalon) phải sửa scoreboard. Cải thiện: (1) đưa backdoor vào một abstract class trong config object (cfg.peek), mỗi DUT có hiện thực riêng; (2) dùng uvm_reg/uvm_mem backdoor (RAL) để scoreboard chỉ hỏi model; (3) giữ interface làm nơi duy nhất biết path. Tất cả đều là dependency inversion.

Làm sao để kết luận test PASS/FAIL ở cuối một cách ổn định cho script regression?

Lấy số lỗi từ uvm_report_server (get_severity_count(UVM_ERROR/UVM_FATAL)) và điều kiện “đã so đủ” (n_cmp > 0); in một dòng cố định ** TEST PASSED **/** TEST FAILED ** ở UVM_NONE để không bị lọc bởi verbosity. Script chỉ grep dòng đó + UVM_FATAL. Tránh dựa vào dòng summary mặc định (có thể thay đổi định dạng giữa tool).

Self-checking nghĩa là gì? Nó khác test directed như thế nào về cách thiết kế?

Test tự biết đúng/sai nhờ model tham chiếu độc lập (ISS), không cần đáp án tính tay ⇒ chạy được stimulus ngẫu nhiên bất kỳ và nhiều seed. Directed thường kèm đáp án cố định (kiểm một kịch bản). Thiết kế self-checking đòi hỏi: model độc lập, so sánh đầy đủ (per-txn + cuối), và cơ chế “không xanh giả”. Directed vẫn cần để đảm bảo corner case.

Chương trình random dài làm sweep chậm — tối ưu thế nào?

Chỉ quét phần đã chạm: regfile 31 ô là rẻ; memory quét theo keys mà model đã ghi (assoc array) thay vì 0..2047 (Iteration 5). Thêm: tính checksum/ XOR toàn bộ vùng rồi so một lần, chỉ liệt kê chi tiết khi checksum lệch (sweep “hai tầng”).

Có — check_phase chạy sau run_phase. Nhưng nếu drain chưa đủ, dữ liệu cuối thiếu; thêm drain_time hoặc phase_ready_to_end.

★ Dễ

EX2 — Dòng kết luận cố định

Thêm report_phase in ** TEST PASSED **/FAILED bằng uvm_report_server. Viết lệnh grep -q "TEST PASSED" làm tiêu chí pass duy nhất cho regression.
Gợi ý & đáp án tham khảo

In ở UVM_NONE. Nhớ so cả UVM_FATAL: một fatal ở build_phase sẽ khiến dòng của bạn không bao giờ được in — nên “không có dòng PASSED” cũng là FAIL (ngầm định tốt).

★★ Vừa

EX3 — phase_ready_to_end thay repeat(60)

Bỏ repeat (60) @(posedge clk) trong test. Cài phase_ready_to_end trong scoreboard chờ tới khi nhận retire của lệnh halt (instr==0x0000006f) hoặc timeout 200 chu kỳ.
Gợi ý & đáp án tham khảo

Cẩn thận vòng vô hạn nếu halt không bao giờ tới: luôn có timeout (fork … join_any với #timeout).

★★ Vừa

EX4 — uvm_event báo “halt_done”

Monitor trigger uvm_event "halt" khi thấy retire halt lần đầu. Scoreboard wait_trigger rồi sweep trong run_phase (hoặc raise/drop objection quanh sweep). So với cách chờ cố định.
Gợi ý & đáp án tham khảo

Ưu: chính xác. Nhược: nếu chương trình không có halt (firmware lặp vô hạn) cần điều kiện khác — bài toán “khi nào chương trình kết thúc?” cũng quan trọng với firmware thật (Lab 15).

★★ Vừa

EX5 — Checksum hai tầng

Tính XOR của mọi word đã ghi ở cả DUT (peek) và ISS; chỉ khi khác mới liệt kê chi tiết từng word. Đo thời gian mô phỏng so với quét từng word.
Gợi ý & đáp án tham khảo

Rất hữu ích khi vùng nhớ lớn; nhớ XOR có thể bỏ sót lỗi bù trừ (hiếm) — dùng CRC nếu cần.

★★★ Khó

EX6 — Backdoor trừu tượng

Định nghĩa virtual class riscv_state_peek (pure virtual peek_reg/peek_mem) và hiện thực riscv_rtl_peek dùng vif. Scoreboard chỉ giữ handle riscv_state_peek lấy từ cfg. Viết hiện thực thứ hai trả giá trị cố định để chứng minh scoreboard không phụ thuộc DUT.
Gợi ý & đáp án tham khảo

Sau bài này, chuyển sang DUT Avalon ở Lab 15 chỉ cần thêm một hiện thực mới — dependency inversion thực tế.

★★★ Khó

EX7 — Sweep giữa chương trình

Thêm khả năng sweep tại “checkpoint”: sau mỗi N retire, so regfile DUT ↔ model tại đúng thời điểm đó (cần pipeline đã drain đến lệnh N — thực tế khó vì còn lệnh bay!). Thảo luận vì sao chỉ sweep cuối chương trình là an toàn, và đề xuất cách làm đúng.
Gợi ý & đáp án tham khảo

Regfile DUT chứa kết quả của các lệnh đã qua WB, nhưng retire stream đến sau shadow pipeline: bạn phải so với state của model sau lệnh đã retire chứ không phải lệnh vừa phát. Dùng chính ret_valid/tín hiệu “write-back xảy ra” để chốt thời điểm.

★★★ Khó

EX8 — Mutation: giấu lỗi khỏi per-retire

Chèn lỗi RTL: ghi thanh ghi thứ hai khi jal (ghi x5 sai). Per-retire có thấy không? Sweep có thấy không? Giải thích bằng “quan điểm khác nhau” của hai lớp kiểm.
Gợi ý & đáp án tham khảo

Per-retire chỉ so rd khai báo của lệnh; ghi lạ vào x5 không xuất hiện ở cổng retire → chỉ REGSWEEP x5 thấy.
