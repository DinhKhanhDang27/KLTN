6. Lý thuyết ngắn — factory & graceful (+ UVM bên trong)

  1. Factory: vì item tạo bằng type_id::create, ta có thể bảo factory "khi ai tạo riscv_seq_item, trả riscv_illegal_item" — sequence không đổi mà stimulus đổi.
  2. Graceful: opcode không thuộc tập hỗ trợ rơi vào default của control_unit (mọi control=0) → core không ghi reg/mem, PC+4. Đây là hành vi "NOP an toàn".
  3. Align: data_memory dùng {addr[31:2],2'b00} → LW/SW lệch bị căn xuống. JALR xóa bit0.
  4. x0: ghi x0 bị regfile bỏ qua → x0≡0.

6.6. uvm_callback — code đầy đủ

Callback cho phép cắm hành vi vào một điểm hook của component mà không sửa hay kế thừa nó. Bốn bước: định nghĩa lớp callback, đăng ký với component, gọi hook, gắn instance callback từ test.

// (1) tb/agent/riscv_cbs.sv — include TRƯỚC driver/monitor
typedef class riscv_monitor;
class riscv_mon_cb extends uvm_callback;
  `uvm_object_utils(riscv_mon_cb)
  function new(string name = "riscv_mon_cb"); super.new(name); endfunction
  // hook: được gọi sau khi monitor dựng xong item, trước ap.write()
  virtual function void post_sample(riscv_monitor mon, riscv_retire_item tr); endfunction
endclass

// (2)+(3) trong riscv_monitor
class riscv_monitor extends uvm_monitor;
  `uvm_component_utils(riscv_monitor)
  `uvm_register_cb(riscv_monitor, riscv_mon_cb)        // đăng ký
  …
  // trong run_phase, sau khi điền tr, trước ap.write(tr):
  `uvm_do_callbacks(riscv_monitor, riscv_mon_cb, post_sample(this, tr))
  ap.write(tr);
endclass

// (4) callback cụ thể + gắn từ test
class flip_wb_cb extends riscv_mon_cb;
  `uvm_object_utils(flip_wb_cb)
  int unsigned n = 3;                                    // lật ở lần thứ 3
  bit          done;                                     // chỉ lật MỘT lần (idempotent — xem lưu ý xsim bên dưới)
  function new(string name = "flip_wb_cb"); super.new(name); endfunction
  virtual function void post_sample(riscv_monitor mon, riscv_retire_item tr);
    if (!done && mon.retire_count == n && tr.reg_write) begin
      done = 1;  tr.wb_data[0] = ~tr.wb_data[0];           // mô phỏng “DUT sai”
    end
  endfunction
endclass

// trong test (build hoặc start_of_simulation):
flip_wb_cb cb = flip_wb_cb::type_id::create("cb");
uvm_callbacks#(riscv_monitor, riscv_mon_cb)::add(env.agent.mon, cb);     // chỉ monitor này
// uvm_callbacks#(riscv_monitor, riscv_mon_cb)::add(null, cb);           // MỌI monitor (type-wide)
// uvm_callbacks#(riscv_monitor, riscv_mon_cb)::delete(env.agent.mon, cb);  // gỡ

Kết quả mong đợi (đã chạy): scoreboard REG mismatch pc=0x00000008 ...: act x3<=0x0000000c exp x3<=0x0000000d đúng ở retire thứ 3 — lỗi tiêm từ ngoài mà không sửa monitor.

Lưu ý xsim 2023.2: khi cùng lúc có uvm_report_cb::add(null, catcher) (mục 6.7), hook uvm_do_callbacks của monitor bị gọi hai lần cho mỗi item (đo được: post_sample in 2 dòng/lần). Callback lật bit kiểu wb_data[0] = ~wb_data[0] sẽ tự triệt tiêu → không có lỗi nào được tiêm. Vì vậy callback ở trên có cờ done để idempotent. Cần thêm vào riscv_pkg.sv: `include "riscv_cbs.sv" trước riscv_driver.sv/riscv_monitor.sv; trong riscv_monitor thêm `uvm_register_cb(riscv_monitor, riscv_mon_cb) sau `uvm_component_utils và `uvm_do_callbacks(...) ngay trước ap.write(tr).
Vì sao không tiêm lỗi ở driver (lật bit lệnh trước khi nạp ROM)? Scoreboard của lab chạy ISS bằng act.instr lấy từ chính retire của DUT; lệnh đã bị lật bit thì ISS cũng thực thi lệnh bị lật ⇒ khớp và không báo lỗi. Muốn bắt lỗi dạng này cần stimulus-driven check (Lab 9 EX5). Tiêm lỗi “ở đầu ra” (monitor) thì khác: đó mô phỏng DUT trả sai kết quả.

6.7. uvm_report_catcher — negative test không làm đỏ regression

Negative test có thể cố ý gây UVM_ERROR (ví dụ opcode lạ làm illegal_bins trúng). Muốn regression vẫn “xanh” nhưng không nuốt lỗi bất ngờ, dùng catcher: hạ cấp đúng lỗi mong đợi, đếm số lần, và cuối test kiểm đúng bằng kỳ vọng.

class exp_err_catcher extends uvm_report_catcher;
  string       id_match;
  int unsigned n_caught;
  function new(string name = "exp_err_catcher", string id = "SB");   // id phải KHỚP id mà scoreboard dùng (`uvm_error("SB", ...))
    super.new(name);  id_match = id;
  endfunction
  virtual function action_e catch();
    if (get_severity() == UVM_ERROR && get_id() == id_match) begin
      set_severity(UVM_INFO);                     // hạ cấp
      set_message({"[EXPECTED] ", get_message()});
      n_caught++;
    end
    return THROW;                                 // vẫn in ra (đã hạ cấp)
  endfunction
endclass
// test.build:  catcher = new();  uvm_report_cb::add(null, catcher);
// test.check:  if (catcher.n_caught != N_EXPECT) `uvm_error("NEG", "so loi mong doi sai")

6.9. Negative test: “pass” nghĩa là gì

Với DUT này có ba loại kết quả mong đợi, nên ghi rõ trong vPlan: (1) graceful — opcode lạ → NOP, DUT và model đồng ý; (2) known limitation — căn chỉnh thay vì trap (spec muốn trap thì là lỗi!); (3) expected error — chủ ý gây lỗi để chứng minh checker bắt được (dùng catcher + đếm).

7. Iteration 0 — type override sinh opcode không hỗ trợ

tb/agent/riscv_illegal_item.sv 
// tb/agent/riscv_illegal_item.sv — biến thể sinh lệnh KHÔNG hỗ trợ (custom opcode)
`ifndef RISCV_ILLEGAL_ITEM_SV
`define RISCV_ILLEGAL_ITEM_SV
class riscv_illegal_item extends riscv_seq_item;
  `uvm_object_utils(riscv_illegal_item)
  function new(string name="riscv_illegal_item"); super.new(name); endfunction

  // encode trả opcode custom-0 (0001011) -> core coi NOP (default control)
  function bit [31:0] encode();
    if (use_raw) return raw_word;
    // {funct7, rs2, rs1, funct3, rd, opcode=0001011}
    return {7'd0, rs2, rs1, 3'b000, rd, 7'b0001011};
  endfunction
endclass
`endif
tb/test/riscv_neg_tests.sv — negative_opcode_test 
`ifndef RISCV_NEG_TESTS_SV
`define RISCV_NEG_TESTS_SV
class negative_opcode_test extends riscv_base_test;
  `uvm_component_utils(negative_opcode_test)
  function new(string n,uvm_component p); super.new(n,p); endfunction

  function void build_phase(uvm_phase phase);
    super.build_phase(phase);
    // MỌI riscv_seq_item do sequence tạo -> riscv_illegal_item
    set_type_override_by_type(riscv_seq_item::get_type(),
                              riscv_illegal_item::get_type());
  endfunction

  virtual function uvm_sequence#(riscv_seq_item) get_seq();
    return riscv_rtype_seq::type_id::create("seq");  // seq cũ, nhưng item bị override
  endfunction

  task run_phase(uvm_phase phase);
    uvm_sequence#(riscv_seq_item) seq = get_seq();
    phase.raise_objection(this);
    seq.start(env.agent.sqr);
    repeat (30) @(posedge cfg.vif.clk);
    // kỳ vọng: KHÔNG thanh ghi nào đổi (toàn NOP) -> x1..x31 = 0
    env.sb.final_check();    // sweep: regfile == ISS (ISS cũng NOP) -> all 0
    phase.drop_objection(this);
  endtask
endclass
`endif

8. Iterations

Iteration 1 — instance override (chỉ 1 nhánh)

Dùng set_inst_override_by_type("env.agent.sqr.*", riscv_seq_item::get_type(), riscv_illegal_item::get_type()).

Khác biệt

Chỉ item tạo dưới sequencer bị thay; chỗ khác vẫn bình thường. Dạy: override phạm vi hẹp theo đường dẫn.

Iteration 2 — negative: ghi x0 (JAL x0) — bất biến

directed jal x0, +8 nhiều lần; kiểm x0=0, các reg khác không đổi bất ngờ.

Khác biệt

reg_write=1,rd=0 nhưng regfile bỏ ghi. SVA x0≡0 (Lab 8) không fail; scoreboard bỏ qua wb khi rd=0. Dạy: x0 bất biến.

Iteration 3 — negative: LW/SW lệch (addr=0x22)

directed SW tới 0x22; kiểm DUT ghi vào word 0x20 (căn chỉnh) và ISS khớp.

Khác biệt

Cả hai căn chỉnh xuống → vẫn khớp. Dạy: hành vi căn chỉnh là "đúng theo RTL"; nếu muốn báo lỗi misalign cần logic trap (DUT không có) — ghi vào verification plan là "known limitation".

Iteration 4 — negative: JALR tới địa chỉ lệ (bit1=1)

addi x1,x0,6; jalr x0,x1,0 → đích 6 (bit0 xóa, bit1 giữ).

Khác biệt

ISS &~1 khớp DUT → PC=6, fetch word index 1. Dạy: bẫy JALR; coverage SVA align bit0 (Lab 8) vẫn pass.

Iteration 5 — uvm_callback tiêm lỗi ở monitor (code đầy đủ ở §6.6)

Định nghĩa riscv_mon_cb với hook post_sample(mon, tr); monitor gọi `uvm_do_callbacks trước ap.write; flip_wb_cb lật 1 bit wb_data ở retire thứ 3 để scoreboard bắt lỗi.

Khác biệt

Không sửa monitor vẫn tiêm được lỗi → REG mismatch đúng retire thứ 3. Gỡ callback (delete) thì sạch. Lưu ý: tiêm lỗi ở driver (lật bit lệnh khi nạp ROM) không bị scoreboard “observation-driven” thấy vì ISS thực thi chính lệnh đã lật — xem EX4.

12. Phỏng vấn — hỏi & đáp

Bấm câu hỏi để xem đáp án — nên tự trả lời miệng trước khi mở. Mỗi câu có ví dụ cụ thể như khi bị hỏi trong phỏng vấn.

Factory override không có tác dụng. Liệt kê các nguyên nhân và cách xác minh.

Theo xác suất: (1) đối tượng tạo bằng new() thay vì type_id::create; (2) override đặt sau khi đối tượng đã được tạo (set trong test nhưng env dựng ở super.build_phase chạy trước); (3) lớp override không đăng ký (`uvm_*_utils) hoặc không biên dịch trong package; (4) instance path sai (tương đối this); (5) method không virtual nên kiểu đổi mà hành vi không đổi; (6) một override khác (instance) ưu tiên cao hơn che mất.

Xác minh: uvm_factory::get().print(), debug_create_by_type, in obj.get_type_name() ngay sau create.

Type override và instance override khác nhau thế nào? Nếu có cả hai?

Type: mọi create của kiểu gốc trong toàn môi trường. Instance: chỉ đường dẫn khớp. Khi cả hai cùng áp dụng cho một đối tượng, instance thắng. Ví dụ: type override riscv_seq_item → riscv_illegal_item cho cả hai agent, rồi instance override agent_b.sqr.* → riscv_seq_item (trả về mặc định) ⇒ chỉ agent_a gặp lệnh lạ.

Vì sao nên đặt override trước super.build_phase trong test?

super.build_phase của riscv_base_test tạo env → agent → driver/monitor/sequencer bằng type_id::create. Override đặt sau thì các component đó đã được tạo bằng kiểu gốc ⇒ override không áp dụng cho chúng (chỉ áp dụng cho đối tượng tạo về sau như item ở run_phase). Quy ước: cấu hình factory và config_db trước, rồi mới gọi super.build_phase.

function void build_phase(uvm_phase phase);
  set_type_override_by_type(riscv_monitor::get_type(), riscv_monitor_dbg::get_type());  // trước
  super.build_phase(phase);                                                              // env dựng với monitor_dbg
endfunction
Khi nào dùng callback thay vì kế thừa + factory override?

Callback: cần chèn một hành vi nhỏ tại điểm hook và muốn bật/tắt/xếp chồng nhiều hành vi độc lập mà không tạo cây kế thừa (ví dụ 5 loại error injection). Factory: cần đổi toàn bộ hành vi/kiểu của một lớp (item mới, driver khác giao thức). Đánh đổi callback: phải có sẵn hook (thiết kế component từ trước), thứ tự thực thi giữa các callback cần quản lý (UVM_PREPEND/APPEND).

Viết các bước tạo và gắn một callback cho driver. Lỗi hay gặp?

(1) class my_cb extends uvm_callback với hook virtual function void pre_xxx(...); (2) trong component: `uvm_register_cb(Comp, my_cb); (3) tại điểm hook: `uvm_do_callbacks(Comp, my_cb, pre_xxx(this, args)); (4) từ test: uvm_callbacks#(Comp, my_cb)::add(inst_or_null, cb). Lỗi hay gặp: quên bước (2) → compile/runtime báo type chưa đăng ký; gắn add khi chưa có instance (handle null → thành type-wide); hook là task nhưng gọi trong function; lớp callback tham chiếu component trước khi khai báo (cần typedef class).

uvm_report_catcher dùng khi nào? Rủi ro?

Dùng để xử lý UVM_ERROR/UVM_WARNING mong đợi ở negative test: hạ cấp, đổi thông điệp, hoặc nuốt (CAUGHT), và đếm để cuối test xác nhận số lỗi mong đợi. Rủi ro: catcher quá rộng (bắt mọi SB error) sẽ che lỗi thật; nên khớp theo ID + chuỗi thông điệp, giới hạn theo test, và luôn kiểm đếm cuối test.

Negative test của lab PASS khi “DUT xử lý nhã nhặn”. Khác gì với bug? Ai quyết định?

Quyết định bởi đặc tả. Căn chỉnh địa chỉ lệch xuống (addr&~3) là đúng nếu spec nói vậy; sai nếu spec yêu cầu misaligned exception. Quy trình: ghi vào vPlan “hành vi mong đợi + nguồn spec”; nếu DUT khác spec → bug; nếu spec mơ hồ → hỏi designer và ghi “known limitation”. Test PASS nghĩa là DUT và model đồng ý và cả hai khớp spec.

type_id::create trả về kiểu của lớp gốc. Khi nào cần $cast? Ví dụ.

Handle có kiểu của lớp gốc nên chỉ thấy field/method của lớp gốc. Truy cập thành viên riêng của lớp override cần $cast:

riscv_seq_item it = riscv_seq_item::type_id::create("it");   // thực tế là riscv_illegal_item (nếu override)
riscv_illegal_item ill;
if ($cast(ill, it)) ill.bad_funct7 = 7'h55;                    // truy cập field chỉ có ở lớp con
else `uvm_info("T", "override khong ap dung", UVM_LOW)

Cách khác tốt hơn: đặt knob ở lớp gốc hoặc dùng virtual để không phải cast.
